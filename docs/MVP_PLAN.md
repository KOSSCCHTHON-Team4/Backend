## 1. 서비스 정의와 목표

### 1.1 한 줄 정의

**관심 지역에서 나의 장소 취향에 맞는 익명의 경험을 하루 한 편 받아 읽고, 마음에 드는 내용을 개인 기록으로 간직하는 장소 기반 SNS.**

사용자는 수신 기준 위치 하나와 4개 분위기 축의 선호를 설정하고, 원하는 장소를 자연어로 선택 묘사한다. 서비스는 반경 안의 적격 LETTER를 고정 분위기로 먼저 점수화한다. 최고점 후보가 여럿일 때만 자연어 설명으로 비교하고 최종 한 편을 정기 배달한다.

**배달 약속:** 매일 한국 시각 09:00에 정기 배달을 실행한다. 적격 후보가 있으면 최고점 한 편, 없으면 0개다. 최소 매칭 점수는 두지 않는다. 미선정된 적격 LETTER는 이후에도 후보로 남는다. 정시 이후 가입·새 후보 발생·배달 후 원문 삭제에 대한 당일 보충·대체는 없고, 서버 장애로 지난 날짜의 수량을 나중에 채우지도 않는다. 당일의 미완료 오류 작업은 같은 서비스 날짜 안에서 재시도할 수 있다.

### 1.2 핵심 가치와 흐름

작성자는 관계를 먼저 맺지 않아도 경험을 공유하고 누적 좋아요 수로 반응을 확인한다. 수신자는 선정된 한 편을 받고, 쌓인 편지를 분위기와 장소 카테고리로 탐색한다. 좋아요는 취소 없는 한 번의 동작으로 수신자 소유의 독립 PRIVATE 경험을 만든다.

**핵심 흐름: 경험 작성·4축 확인 → 안전 처리 → 일일 후보 → 사용자별 한 편 확정 → 익명 열람 → 좋아요·독립 PRIVATE 복사 → 작성자 반응 확인·개인 재열람.**

‘전체 보기’는 실제로 배달받은 편지 전체다. 지역의 미선정 LETTER 전체에 대한 접근 권한을 뜻하지 않는다.

### 1.3 약속하지 않는 것

모든 작성물의 배달, 모든 날짜의 편지 공급, 장소의 객관적 업종·현재 분위기·실제 방문 인증, 현재 감정 진단, 지속적 친구 관계·외로움 완화·사업성 검증을 보장하지 않는다. 4축은 서비스에서 사용하는 취향 표현이며, 장소의 객관적 평가 점수나 심리검사가 아니다. 자체 카테고리를 네이버의 공식 업종 분류라고 표시하지 않는다.

## 2. 문제 가설과 검증 범위

### 2.1 수용한 문제 가설

> 일상의 장소에서 느낀 경험과 감정을 누군가와 나누고 싶지만, 그 이야기에 공감할 상대를 찾기 어렵고 먼저 관계를 맺거나 대화를 시작하는 것은 부담스러운 사람들이 있다. 나누고 싶었던 기억이 개인 기록에 머물거나 공유를 포기하게 되는 문제가 있는지 검증한다.

사용자가 불특정 다수 인터뷰로 근거를 보충한다. 사회 전체의 교류가 감소한다거나 기존 SNS에 경험 공유가 없다는 포괄적 주장을 전제로 삼지 않는다.

### 2.2 이번 구조의 검증 가설

| ID | 가설 | 주의할 해석 |
|---|---|---|
| H1 | 관심 지역의 경험이라는 맥락이 낯선 사람의 글을 읽을 이유가 된다. | 글 자체의 흥미와 지역의 효과를 구분한다. |
| H2 | 작성자가 좋아요·보관 반응을 확인하면 다시 작성할 동기가 생긴다. | 매칭으로 실제 배달 기회를 얻었는지부터 확인한다. 반응과 재작성의 상관을 인과로 단정하지 않는다. |
| H3 | 팔로우·답장 없이도 익명 LETTER를 작성하고 공유한다. | 개인 답장보다 우수하다는 비교 가설은 아니다. |
| H4 | 4축 선호 매칭이 하루 한 편의 적합도를 높인다. | 축 분류 정확도와 추천을 좋아하는지는 다른 평가다. |
| H5 | 자연어 설명이 고정 분위기 최고점 동률에서 선택 품질을 보완한다. | 자연어가 실제 사용된 매칭만 분리해서 평가한다. |
| H6 | 분위기·장소 카테고리 필터가 받은 편지를 다시 찾는 데 도움이 된다. | 하루 한 편 구조에서는 기록이 쌓인 뒤 평가할 필요가 있다. |
| H7 | 직접 PRIVATE와 LETTER 복사 PRIVATE를 재열람할 가치가 있다. | 복사 횟수와 실제 재열람을 구분한다. |

4개 축을 모두 선택하는 온보딩·작성 확인의 부담, 내용이 적은 경험의 오분류, 비슷한 글만 선택되는 편중, 한번도 배달되지 않는 작성물의 비율은 검증 대상이다. 사용자 선택이나 AI 분류만으로 성향이 안정적이거나 매칭 효과가 입증됐다고 표현하지 않는다.

## 3. 핵심 개념과 확정 정책

### 3.3 이전 결정과 충돌하는 부분

Q1·Q3의 ‘지역 내 전체 배달’은 Q19의 ‘하루 한 편 선정’으로 대체되었다. 이번 답변으로 8축 가정은 4축으로 정정하고, 네이버 분류표 확보를 자체 카테고리 8종으로 대체한다.

**Q26 B는 Q22 A보다 더 구체적인 분위기 입력 규칙이다.** 분위기는 최종 저장 시 4축이 모두 필요하다. 반면 장소 카테고리는 여전히 미분류 저장을 허용한다. AI의 추론 결과가 불완전한 것과 최종 저장 데이터가 불완전한 것을 혼동하지 않는다.

Q27 A에 따라 후보는 다음 날에도 남지만, 온보딩 전 이미 후보가 된 LETTER를 신규 사용자에게 소급 제공하지 않는 원칙은 유지한다. 정확한 준비 완료 시각의 정의는 6장 제안과 17장 계약에 따른다.

반응이 적은 이유를 노출 부족과 열람 후 무반응으로 구분해 검토하는 것을 권한다. 재노출 뒤 열람·반응·작성자 재작성 및 숨김·신고를 함께 보아야 한다. 현재 사업성·수익 효과를 검증한 것으로 설명하지 않는다.

## 5. 사용자 흐름

### 5.1 최초 설정

초대 확인·로그인 → 지도에서 수신 기준 위치·고정 반경 확인 → **4개 분위기 축마다 -1 또는 +1을 모두 선택** → 원하는 장소 분위기 자연어 설명 선택 입력 → 외부 AI 활용 목적 안내 확인 → 설정 완료.

축 누락·중복·0·범위 밖 값이면 온보딩을 완료하지 않는다. 자연어 설명은 없어도 된다. 위치 확정 후 변경 불가를 안내한다. 4축 선호와 설명은 이후 수정할 수 있다. -1/+1은 부정적·긍정적 평가가 아니라 양쪽 선택값을 구분하는 숫자다.

09:00 이후 온보딩을 완료한 사용자는 다음 날 09:00 정기 배달부터 대상이 된다. 09:00 이전에 완료했더라도 그날 컷오프까지 적격 후보가 있어야 한 편을 받는다. 가입 직후 과거 LETTER를 소급 제공하거나 임의 첫 편지를 추가하지 않는다. 정확히 경계 시각에 완료한 경우의 포함 기준은 6.2장의 시간 계약으로 통일한다.

### 5.2 직접 LETTER 작성

네이버 지도에서 특정 위치 클릭 → 핀 좌표 확인 → 필수 본문 입력 → JPG·PNG 사진 선택 → AI가 본문에서 4축·자체 카테고리를 추론 → 작성자가 결과 확인·수정 → **부족한 분위기 축을 직접 채워 4축 완성** → 카테고리는 0~3개 확정 → 최종 저장·안전 처리 → 일일 매칭 후보 → 선정된 사용자에게 배달.

AI가 근거를 찾지 못한 축은 작성 중 분석 응답에서 미결로 보여줄 수 있다. 그 경우 저장 버튼을 막고 해당 축의 직접 선택을 요청한다. 본문·업로드 내용을 불필요하게 잃게 하지 않는다. **필수 입력을 충족하기 위해 AI가 근거 없는 값을 확정하거나 계정 취향을 복사하지 않는다.**

게시 직후 반경 안 전원에게 전달하지 않는다. 미선정된 적격 기록은 이후 날짜에도 후보로 남는다. 경험 위치는 본인의 수신 기준 위치와 달라도 된다. 장소 핀·AI 분류는 방문 인증이 아니다.

네이버 지도 클릭의 좌표와 화면 픽셀은 구분한다. FE는 핀의 위도·경도를 명시적으로 전송하며 AI는 핀 위치를 변경하지 않는다. 좌표 취득·주소 변환·자체 카테고리 분류는 별도 역할이다. [S8][S9][S10]

게시 안내 제안: **“이 경험은 주변 사용자의 하루 한 편 후보가 됩니다. 선정된 수신자에게 익명으로 전달되며, 상대가 개인 보관함에 복사한 내용은 원문을 삭제해도 남을 수 있습니다.”**

### 5.3 수신·재열람

일일 선정으로 수신 항목 확정 → 수신함 진입·새로고침 → 지금까지 받은 편지 전체 → 필요 시 분위기·카테고리 필터 → 익명 상세 → 좋아요하고 보관 → 새 PRIVATE 본문·분류·이미지 생성 → BOOKMARK 재열람.

하루 수신 개수 제한과 수신함 전체 열람 개수 제한을 혼동하지 않는다. 오늘 1개를 받아도 과거 수신 이력은 계속 열람할 수 있다. 필터가 0건을 만들었다고 새 편지를 추가 선정하지 않는다.

### 5.4 직접 PRIVATE

핀·본문·선택 사진 → 외부 AI 처리 안내 → 분위기·카테고리 분석 → 저장 전 확인·수정 → **4축 필수 완성, 카테고리는 0~3개** → 본인 보관함에 저장.

직접 PRIVATE도 Q24 A에 따라 AI 분석 대상이다. AI가 실패하면 사용자가 분위기 4축을 직접 채워 저장할 수 있고, 카테고리는 미분류를 허용한다. PRIVATE는 일일 후보에 넣지 않는다. LETTER_COPY는 유효한 원문의 4축·카테고리를 복사하므로 재분석이나 수신자의 추가 4축 입력을 요구하지 않는다.

### 5.5 설정 변경

수신 위치는 변경할 수 없다. 4축 선호와 자연어 설명은 수정할 수 있다. 수정한 선호는 앞으로의 선정에 적용하고, 이미 확정된 수신 이력·원문·PRIVATE는 변경하지 않는 방향을 권한다. 하루 중 반복 변경으로 추가 편지를 받는 우회는 허용하지 않는 방향이다.

## 6. 하루 한 편 매칭 및 필터 규칙

### 6.1 확정된 선정 순서

```text
서버의 일일 정기 배달 실행
  → 지역·시간·안전·권한·미수신 조건으로 후보 구성
  → 후보가 없으면 그 날짜는 후보 없음 상태
  → 후보가 있으면 고정 분위기 4축으로 1차 점수 계산
  → 1차 최고점 후보만 남김(최소 점수 기준 없음)
  → 최고점이 1개면 즉시 선정, 자연어 평가 불필요
  → 여러 개이고 선택 자연어 설명이 있으면 그 후보끼리만 비교
  → 설명 없음·평가 실패·남은 동률이면 최고점 범위 안에서 무작위 해소
  → 사용자·날짜별 결과 한 번 확정, 실제 선정한 LETTER만 수신 이력 생성
```

최저점 후보만 있어도 적격 후보가 있다면 최고점 한 편을 선정한다. ‘조건이 완벽히 맞는 글만 보낸다’고 안내하지 않는다. 카테고리는 수신함 조회 필터이며, 현 단계에서 가산점·제외 조건으로 사용하지 않는다.

### 6.2 후보 기간과 이월

**확정:** 온보딩 이후 수신 자격이 생긴 미수신 LETTER는 다음 날에도 후보로 남는다. 최근 24시간·7일 같은 만료 기간을 임의로 추가하지 않는다. 이미 받은 기록·삭제·운영 숨김·안전 미승인·반경 밖·자기 글·PRIVATE·PUBLIC은 제외한다.

**시간 구현 제안:** `available_at`은 최초로 안전·분류·게시 준비를 마쳐 후보로 사용할 수 있게 된 시각이다. `mailbox_enabled_at`은 유효한 온보딩 완료 시각, `cutoff_at`은 해당 일일 실행의 기준 시각이다. 다음과 같이 한 실행의 시간 범위를 고정한다.

```text
Memory.type == LETTER
AND Memory.status == ACTIVE
AND 4축 최종 분류가 모두 유효함
AND 수신자 계정이 초대·접근 허용 상태임
AND memory.owner_id != receiver.id
AND mailbox_enabled_at <= memory.available_at <= cutoff_at
AND 경험 핀과 수신 기준 위치의 거리 <= 고정 반경
AND 해당 receiver에게 동일 memory의 과거 배달 이력이 없음
```

이는 초안 기술 계약이다. 최초 준비 완료 시각을 매칭에 유리하도록 매일 갱신하지 않는다. 온보딩 직전 작성·직후 안전 승인 같은 경계는 이 시각 정의대로 테스트한다. 정확한 동일 시각 비교와 DB 정밀도는 0~2시간에 통일한다.

한 사용자가 받았다고 원문을 전역 후보에서 소비하지 않는다. 같은 LETTER가 서로 다른 사용자에게 선정되는 것은 가능하며, 동일 사용자에게만 재배달하지 않는다. 후보 이월이 언젠가 반드시 배달된다는 보장은 아니다.

### 6.3 1차 점수 공식 — Q34 A 확정

축 순서는 사용자 지정 순서인 **혼잡도 / 공간감 / 동행 적합성 / 체류 적합성**으로 고정한다. 실제 값은 각 축 `-1` 또는 `+1`이다. 내부 축 이름은 구현용 제안이며 사용자에게 표시할 양쪽 문구는 9장의 확정값을 사용한다.

**확정된 동일 가중치·일치 축 수 방식:**

```text
S_fixed(u, m) = sum(1 if u[i] == m[i] else 0, i = 1..4)
             = (4 + sum(u[i] * m[i], i = 1..4)) / 2
```

| 일치 축 | 점수 |
|---:|---:|
| 4개 | 4 |
| 3개 | 3 |
| 2개 | 2 |
| 1개 | 1 |
| 0개 | 0 |

-1을 선택했다고 점수가 깎이거나 +1 장소가 좋은 평가를 받는 구조가 아니다. **같은 쪽인지**를 비교한다. 0은 선택값으로 저장하지 않지만, 총 매칭 점수 0점은 정상이다.

예시: 사용자 `(-1,-1,-1,-1)`에게 경험 A `(-1,-1,+1,-1)`와 경험 B `(-1,+1,-1,-1)`는 모두 3점이다. 경험 C `(+1,+1,-1,-1)`는 2점이다. 자연어 비교는 A·B에만 수행하고 C는 제외한다. 확률적 모델이나 경험적 추천 성능 주장이 아닌 설계 산식이다.

Q26 B에 따라 최종 후보는 4축이 모두 채워져 있으므로 UNKNOWN 점수 보정은 필요하지 않다. 유효하지 않은 과거·시드 데이터는 후보가 아니라 데이터 오류로 처리하고 수리한다. 가능한 4축 조합은 2^4=16개, 위 점수값은 5종이므로 같은 조합 또는 같은 점수의 여러 후보가 생길 수 있다.

### 6.4 자연어 동률 비교와 마지막 무작위

**확정:** 고정 분위기의 최고점 동률 후보만 자연어 비교 대상이다. 자연어는 1차 점수와 합산하지 않으며, 사용자 선택값을 덮어쓰지 않는다. 선택 설명이 없으면 이 단계를 생략한다.

**구현 제안:** 사용자의 설명과 동률 후보의 본문·분류를 최소 입력으로 제공하고, 제공한 후보 ID 안에서 순위를 반환하게 한다. 계정 ID·이메일·작성자 신원·불필요한 위치는 입력하지 않는다. 본문의 지시문을 분류·선정 규칙으로 실행하지 않는다. 출력 형식 제한만으로 내용상 정확성이 보장되는 것으로 취급하지 않는다. [S11]

자연어 평가가 단독 1위를 정하면 그 후보를 선택한다. 공동 1위만 남긴 유효한 결과라면 그 집합에서 무작위로 해소하는 안을 권고한다. 설명이 없거나 평가 결과 전체가 실패·무효라면 1차 최고점 집합에서 무작위로 정한다. 어느 경우에도 1차 점수가 낮은 후보로 넘어가지 않는다.

무작위는 사용자·날짜별로 결과를 저장하고 같은 날짜 새로고침·중복 작업에서 재추첨하지 않는다. 비동기 작업 중 후보가 삭제되면 실제 확정 전에 후보 상태를 재검사한다. 후보 전체를 FE에 노출하지 않는다.

동률 평가 모델·후보 상한·토큰 한도·실패 조건·시간 초과는 0~2시간 AI/BE 계약이다. 직접 LLM 비교 또는 임베딩 비교는 구현 대안이며 pgvector를 필수로 추가하지 않는다. 후보 일부만 임의로 제외하는 별도 추천 정책은 사용자 합의 없이 만들지 않는다.

### 6.5 정기 배달과 하루 한 번의 확정

**확정:** 정기 배달은 매일 한국 시각 **09:00 (`Asia/Seoul`)**에 서버에서 실행한다. 서비스 날짜도 같은 시간대의 달력 날짜를 사용한다. 사용자가 접속하지 않아도 대상이면 수신 기록을 만들고, 수신함 진입·수동 갱신은 저장된 기록을 조회한다. 푸시·자동 폴링·조회 때 새 선정은 제공하지 않는다.

각 사용자에게 같은 서비스 날짜의 성공 배달은 **최대 1개**다. 적격 후보가 없으면 0개이며, 후보가 있다는 사실이 어떤 특정 글의 배달을 보장하지는 않는다. 모델·DB 처리에 소요되는 시간과 실제 완료 시각은 `delivered_at`으로 구분한다.

| 정기 배달 상황 | 최종 제품 동작 |
|---|---|
| 09:00 기준 대상이며 적격 후보 있음 | 가장 높은 4축 점수 → 필요한 동률 해소 → 한 편 확정 |
| 09:00 기준 후보 없음 | 그날은 0개. 오후에 새 후보가 생겨도 당일 보충하지 않음 |
| 09:00 이후 신규 온보딩 | 다음 정기 배달 대기. 당일 첫 편지를 별도 생성하지 않음 |
| 사용자가 접속하지 않음 | 다른 조건을 만족하면 정상 배달. 미접속과 서버 장애를 구분 |
| 같은 날 반복 실행·새로고침·필터 변경 | 확정 결과 재사용. 새로운 편지를 더 생성하지 않음 |
| 배달 성공 뒤 원문 삭제 | 원문 열람 차단, 당일 대체 없음. 성공한 PRIVATE 복사본은 유지 |
| 자연어 비교만 실패 | 1차 최고점 집합에서 무작위 대체 판단으로 한 편 선정 가능 |
| 당일 서버·DB 작업 실패 | 성공하지 않은 작업만 같은 날 재시도 가능. 중복 성공 금지 |
| 실패한 서비스 날짜가 이미 지남 | 그 날짜분을 새로 배달하지 않음. 과거 누락량을 오늘 수량에 합산하지 않음 |
| 실패로 보였지만 수신 기록은 이미 저장됨 | 기존 성공 결과를 복구·조회. 새 편지를 생성하지 않음 |

#### 6.5.1 정상적인 후보 없음과 오류를 구분한다

`NO_CANDIDATE`는 정기 배달 검사가 정상 완료됐지만 후보가 없는 결과다. 나중에 후보가 생겼다는 이유로 해당 날짜를 다시 열지 않는다. 반면 서버·DB 오류는 결과를 아직 확정하지 못한 상태이므로 Q38 A 범위에서 당일 복구가 가능하다. 삭제된 편지도 이미 배달을 성공했다면 일일 수량을 되돌리지 않는다.

**구현 제안:** 날짜별 작업 상태는 아래처럼 분리할 수 있다. 실제 enum명과 응답 필드는 0~2시간 계약 대상이다.

| 상태 예시 | 의미 | 재실행 원칙 |
|---|---|---|
| `PENDING` | 정기 시각을 기다리는 대상 | 정기 작업만 시작 |
| `PROCESSING` | 해당 날짜의 선정·저장 처리 중 | 중복 작업을 합치거나 차단 |
| `DELIVERED` | 한 편의 수신 기록 저장 성공 | 결과 유지, 삭제 후에도 슬롯 재사용 없음 |
| `NO_CANDIDATE` | 기준 시각의 적격 후보가 없음 | 그날 추가 탐색·배달 없음 |
| `RETRYABLE_ERROR` | 아직 성공하지 않은 일시 오류 | 같은 서비스 날짜 안에서만 재시도 |
| `EXPIRED_ERROR` | 날짜가 지나 더 이상 배달하지 않는 실패 | 과거 날짜 새 수신 생성 금지 |

정시 이후 가입한 계정의 오늘 상태는 ‘아직 수신 대상이 아님/다음 배달 대기’로 표시하는 안을 권한다. 이 상태와 ‘오늘 검사를 마쳤으나 후보 없음’은 구분한다. 이를 위해 가입 이전 날짜의 불필요한 DailySelection 행을 반드시 생성할 필요는 없다.

#### 6.5.2 컷오프·설정·재시도 — 구현 계약 제안

`DailySelection(user_id, service_date)`에 날짜별 작업을 두고 `cutoff_at`은 해당 날짜의 예정 배달 시각 09:00으로 고정하는 안을 권한다. 실제 실행이 지연돼도 정시 이후 가입자나 신규 후보를 그날 추가하지 않는다. 재시도에서는 동일 컷오프와 동일 취향 스냅샷을 재사용하되, **삭제·숨김·접근 제한 등 현재의 안전·권한 상태는 다시 검사**한다.

09:00 직전의 유효한 4축·자연어 설정을 불변 스냅샷 또는 참조 가능한 버전 이력으로 재현하는 방법을 팀이 정한다. 버전 번호만 저장하고 해당 버전의 값은 남기지 않는 방식으로 재현 가능하다고 가정하지 않는다. 첫 실행 자체가 지연되거나 서버가 완전히 중단됐을 때의 설정 재현 방법도 기술 계약에 포함한다. 정시 설정을 재현할 수 없는데도 복구 시점 설정으로 몰래 대체하지 않는다.

이미 성공한 결과는 취향 수정·필터 변경·재로그인으로 바꾸지 않는다. 수정된 취향은 다음 정기 선정에 적용하는 안을 권한다. 데이터 변경과 모델 호출이 경합하면 확정 직전에 후보 상태와 날짜를 다시 확인한다.

**날짜 경계 보호:** 전날 작업이 자정 이후 늦게 응답하더라도 전날 수신 기록을 신규 확정하지 않는 방식으로 Q38 A를 적용한다. 저장이 이미 성공했던 결과의 조회·복구와, 과거 날짜에 새로운 수신을 만드는 행위를 구분한다. 정확한 잠금·날짜 검사·재시도 상한은 기술 계약으로 정한다.

이 절은 앱 내부 기능의 명세다. 실제 자동화·서버 스케줄을 이 문서 작성 과정에서 생성하거나 실행한 것은 아니다.

### 6.6 누적 수신함의 조회 필터

기본은 **이미 받았고 지금도 열람할 수 있는 편지 전체**다. Q33 A에 따라 조회에 사용할 분위기 축·값은 계정 설정과 별도로 선택한다. 계정의 4개 선택값을 자동으로 OR 필터에 넣지 않는다. 조회는 매칭 점수 계산이나 새 배달을 유발하지 않는다.

```text
(분위기 조건 없음 OR 조회에서 선택한 축·값 중 하나 이상 일치)
AND
(카테고리 조건 없음 OR 선택 카테고리 중 하나 이상 일치)
```

예: ‘조용한’을 선택하고 카테고리 ‘카페 / 공부·작업 공간’을 선택하면 조용하면서 둘 중 하나에 해당하는 편지만 표시한다. 여러 분위기 값의 내부 OR를 승인 없이 AND로 변경하지 않는다.

필터를 해제하면 누적 수신 목록으로 돌아온다. 카테고리 미분류 기록은 전체 보기에서 보이지만 특정 카테고리 조건에는 일치하지 않는다. 필요하면 미분류 상태 필터를 후속 검토하되 이번의 자동 필수 기능으로 추가하지 않는다. 필터 결과가 0개라도 새 편지를 추가하지 않는다.

### 6.7 원문 삭제와 후보 상태 변화

원문 일반 삭제·운영 숨김 이후에는 그 원문을 새로 선정하거나 새 PRIVATE로 복사하지 않는다. 이미 받은 편지의 원문 본문·이미지도 열람을 차단한다. 이미 성공한 독립 PRIVATE의 내용·분류·이미지는 유지한다.

최종 수신 확정 전 원문이 무효가 된 경우와, 성공한 수신이 나중에 삭제되는 경우는 다르다. 전자는 아직 성공하지 않은 같은 날짜 작업의 재검사·복구다. 남은 유효 후보가 있으면 동일 규칙으로 다시 계산하고, 없다면 내용을 배달하지 않는다. 후자는 Q37 A에 따라 **당일 대체 없이 종료**한다. 수신함에 삭제 안내를 남길지 항목을 숨길지는 FE/BE 계약으로 통일하며, 어느 쪽도 내용 노출이나 추가 수신을 허용하지 않는다.

## 7. 좋아요와 독립 PRIVATE 복사

### 7.1 사용자가 보는 동작

버튼은 **‘좋아요하고 보관’**, 성공 후에는 **‘복사 완료’** 등으로 표시한다. 좋아요 취소는 없으며 같은 수신 편지에서 한 번만 실행한다.

복사본을 BOOKMARK에서 삭제해도 원문 좋아요는 취소되지 않는다. 같은 편지에서 다시 복사하지 않으며, 좋아요 수는 현재 살아 있는 보관본 수가 아니라 성공한 누적 동작 수이다.

### 7.2 독립 저장 규칙

| 항목 | 새 PRIVATE 경험 |
|---|---|
| 식별자 | 새 ID |
| 소유자 | 편지를 받은 사용자 |
| 종류 | `PRIVATE` |
| 생성 유형 | `LETTER_COPY`라는 구분값만 사용 가능 |
| 본문·장소·4축 분위기·카테고리 | 완성된 4축 및 복사 당시 카테고리·상태. 카테고리 미분류이면 그 상태 유지 |
| 이미지 | 있으면 새 PRIVATE용 독립 파일로 보존, 없으면 `NULL` |
| 생성 시각 | 개인 복사본 생성 시각 |
| 원문 연결 | 원문 ID·원작성자 ID·원배달 ID·사본 ID 역참조를 유지하지 않음 |

`DIRECT`와 `LETTER_COPY`를 구분하는 생성 유형은 원문 연결이 아니다. 생성 유형으로 복사본 재공유를 막고, 타인의 경험을 자신이 직접 겪은 기록처럼 표시하지 않도록 한다. 원본을 추적하려는 숨은 연결 테이블을 추가하지 않는다.

카테고리를 추가해도 사본에 원문 연결을 만들지 않는다. 공유 카테고리 사전의 ID를 사용하는 것은 원문 연결이 아니다. 분류·표시값의 과거 상태를 보존하는 스냅샷 방식을 권고하며, 원문을 나중에 재분류하더라도 기존 사본을 갱신하지 않는다. 사본 생성 시 본문을 외부 AI로 다시 보내 재분류하는 과정은 추가하지 않는다.

원래 `LetterDelivery`에는 좋아요 성공 여부와 시각을 기록할 수 있지만, 생성된 PRIVATE ID를 연결하지 않는다. 전체 시스템에서 어떠한 추론도 불가능한 완전 익명화를 약속하는 것은 아니며, 제품 데이터에서 원문·사본의 지속적인 연결을 유지하지 않는다는 뜻이다.

### 7.3 중복·실패 처리 — 구현 제안

서버가 실제 배달 이력, 원문 상태, 미실행 여부를 확인한다. 동시에 같은 요청이 들어와도 **PRIVATE 생성과 좋아요 성공 기록은 한 번만 확정**한다. 클라이언트가 원문 내용을 직접 보내 임의 복사하는 API로 만들지 않는다.

이미지 복사 또는 DB 기록이 실패했다면 성공한 좋아요로 표시하지 않고 재시도할 수 있게 한다. 서버에서 성공했지만 응답이 유실된 경우의 재요청은 새 사본을 만들지 않는다. 이를 위해 배달 행 잠금·트랜잭션 등 BE의 일관성 수단을 명세에서 선택한다.

파일 시스템과 DB 변경은 하나의 자동 롤백 단위가 아니므로 임시 파일·실패 후 정리·중단 후 점검을 설계한다. 원문 삭제와 보관 요청이 겹치면 어느 동작이 먼저 확정됐는지를 기준으로 결과를 일관되게 처리한다.

### 7.4 연결하지 않는 데 따른 기능 경계

원문에서 ‘현재 보관 중인 사본으로 이동’, 원문 수정 동기화, 원문 삭제에 따른 사본 일반 삭제, 사본 삭제에 따른 좋아요 취소는 제공하지 않는다.

신고된 원문과 모든 사본을 원본 ID로 찾아 일괄 회수하는 기능 역시 성립하지 않는다. 이 제약을 숨기거나 자동 회수가 가능한 것으로 설명하지 않으며, 운영 대응은 16장에 따로 기록한다.

### 7.5 이번 변경의 복사 경계

완성된 4축의 -1/+1 값과 분류 출처, 0~3개 자체 카테고리, 사전 버전·표시 스냅샷을 복사한다. 수신자의 매칭 점수·선호 설명·계정 취향·원작성자 계정정보는 복사하지 않는다. PRIVATE 복사는 AI를 재호출하지 않고 원본에 연결하지 않는다.

새 규칙에서 최종 저장된 분위기 UNKNOWN은 없다. 원문이 4축 불완전 상태라면 정상 복사를 진행한 것으로 처리하지 않는다. 카테고리 0개는 유효한 미분류 상태이므로 복사가 가능하다.

### 8.3 익명과 계정 취향

수신자 응답에 원작성자 ID·닉네임·프로필·우편함 위치를 포함하지 않는다. 작성자에게 반응자 목록을 제공하지 않는다. 계정의 4축 선호와 자연어 설명은 본인 설정이며 타인 프로필 공개 기능이 아니다. 운영자는 제한된 관리 경로만 사용한다.

본문·사진 자체의 이름·얼굴까지 자동 익명화됐다고 약속하지 않는다. 파일명·메타데이터·API 오류를 통한 신원 노출도 테스트한다. 추천 근거를 제공한다면 본인의 선호와 선택된 글의 근거만 사용한다.

## 9. 4축 분위기·자체 카테고리·AI

### 9.1 사용자 지정 분위기 4축 — 확정

| 순서 | 내부 축 코드 제안 | -1 | +1 |
|---:|---|---|---|
| 1 | `CROWD_LEVEL` | 조용한 | 북적이는 |
| 2 | `SPATIAL_FEEL` | 아늑한 | 탁 트인 |
| 3 | `COMPANY_FIT` | 혼자 가기 좋은 | 함께 가기 좋은 |
| 4 | `STAY_STYLE` | 오래 머물기 좋은 | 잠깐 들르기 좋은 |

사용자의 문구와 숫자 대응을 그대로 사용한다. ‘북적이는’을 이전 예시 ‘활기찬’으로 바꾸지 않는다. 내부 코드는 팀이 합의할 식별자이며 사용자 라벨의 변경이 아니다. 계정은 네 축 모두 필수이고 현재 감정이 아니라 선호하는 장소 특성을 표현한다.

자연어 설명은 선택이며 공백·미입력도 정상이다. 이후 선호 4축과 설명을 수정할 수 있지만 수신 기준 위치는 바꾸지 않는다.

양쪽 특성은 현실의 모든 공간에서 객관적으로 배타적이라고 주장하지 않는다. **작성 시 그 경험에서 더 가까웠던 쪽을 선택**하도록 안내하는 것을 권한다. 예를 들어 혼자·함께 모두 가능해 보이면 해당 글의 경험 맥락에 맞는 쪽을 작성자가 최종 정한다. 중립 0·세 번째 취향값·연속 슬라이더는 현재 요구가 아니다.

### 9.2 분석 중 미결과 최종 저장의 필수값

| 단계 | 분위기 4축 | 장소 카테고리 |
|---|---|---|
| 계정 설정 | 모두 -1/+1 필수 | 계정 필수 항목 아님 |
| AI 분석 응답 | 근거 없으면 해당 축 미결로 반환 가능 | 근거에 따라 0~3개 제안 |
| 직접 LETTER 최종 저장 | 작성자 보완으로 모두 -1/+1 필수 | 유효 분류 0~3개, 미분류 허용 |
| 직접 PRIVATE 최종 저장 | 동일하게 4축 필수 | 동일하게 0~3개 |
| LETTER_COPY 생성 | 원문의 완성된 4축 복사 | 원문의 값·미분류 상태 복사 |

**Q26 B는 AI에게 강제 추측을 요구하지 않는다.** 근거가 없는 축은 분석 응답에서 `needs_user_input` 또는 `null` 같은 중간 상태로 알리고 작성자가 채운다. 저장된 최종 경험에는 중간 상태를 남기지 않는다. 이 중간 분석 상태를 별도 서버 초안 저장 기능으로 반드시 구현한다는 뜻은 아니다.

AI 오류가 나더라도 작성자가 4축을 직접 입력하면 분류 측면의 저장 조건을 충족할 수 있다. 안전 검사 실패는 별개이며 다른 사용자에게 전달을 허용하지 않는다. 계정 선호를 경험의 빈 축에 자동 복사하거나 기본값을 미리 선택해 제출하지 않는다.

### 9.3 AI 분석과 저장 전 확인 — 구현 제안

최신 경험 본문과 아래 축·카테고리 정의만으로 분류한다. 이미지·네이버 주변 업체 조회를 분류 필수 입력으로 추가하지 않고 핀을 변경하지 않는다. 본문에 등장한 다른 장소와 현재 핀의 경험을 혼동하지 않도록 작성자가 결과를 확인한다.

분위기 축의 출처를 `AI` 또는 `USER`로 구분하고 근거 문구는 본문에서 실제로 확인할 수 있을 때만 기록하는 안을 권한다. 사용자가 직접 선택한 값에 AI가 뒷받침 근거를 꾸며 붙이지 않는다. 축의 필수 완성은 데이터 완결성이지 AI 정확성 검증이 아니다.

본문 수정 후 과거 분석 응답이 도착하면 최신 글에 적용하지 않는다. 사용자 수정값을 늦은 AI 응답으로 덮어쓰지 않는다. 저장 전 수정은 허용하지만 저장 후 PRIVATE 편집은 추가하지 않는다.

허용 축 ID·-1/+1·카테고리 코드·개수·중복을 서버에서 검증한다. 구조화 출력은 형식을 제한하는 보조 수단이며 정확성 보장이 아니다. 본문의 ‘규칙을 무시하라’는 표현은 분석할 데이터이지 실행할 명령이 아니다. [S11]

### 9.4 자체 장소 카테고리 8종 — 목록 확정, 분류 가이드는 제안

아래 8개 명칭은 사용자 Q32에 따른 서비스 자체 분류다. 네이버의 공식 업종 코드·계층과 일치한다고 주장하지 않는다. 내부 코드는 제안이며 운영 정의·포함 사례는 개발 시작 전 팀이 확인한다.

| 내부 코드 제안 | 확정 명칭 | 분류 가이드 제안 |
|---|---|---|
| `CAFE` | 카페 | 음료·카페 이용이 중심인 공간 |
| `RESTAURANT` | 음식점 | 식사 제공·식사 이용이 중심인 공간 |
| `BAR` | 술집 | 술을 마시는 이용이 중심인 공간 |
| `PARK_WALK` | 공원·산책 | 공원·산책로 등 걷거나 쉬는 야외 공간 |
| `CULTURE` | 문화 | 전시·공연·박물관 등 문화 경험을 위한 공간 |
| `STUDY_WORK` | 공부·작업 공간 | 도서관·스터디 공간·공유 작업 공간 등 공부·작업 용도가 드러나는 공간 |
| `SHOPPING` | 쇼핑 | 상품을 둘러보거나 구매하는 매장·시장 등의 공간 |
| `OTHER` | 기타 | 장소 유형의 단서는 있으나 위 7종의 범위에는 해당하지 않는 경우 |

**기타와 미분류의 구분을 권고한다.** 단서가 부족하거나 AI 호출이 실패했으면 `category_ids=[]`와 별도 분석 상태로 남긴다. ‘기타’를 오류 기본값으로 채우지 않는다. 다른 명시 분류가 있으면 ‘기타’를 빈칸 채우기용으로 함께 넣지 않는 방향을 권한다.

네이버 전체 카테고리 수집, 공식 경로 확인, provider code 저장은 이번 MVP의 선행 과제에서 제거한다. 지도 제공자는 여전히 네이버이며 바뀌는 것은 장소 유형 사전의 출처다. 기존 `naver_place_category_research.md`는 검토 이력이지 현재 구현 사전이 아니다.

### 9.5 복수 유형 최대 3개 — Q31 A 확정

본문이 실제로 뒷받침하는 복수 유형을 **최대 3개** 저장한다. 하나만 명확하면 1개, 단서가 없으면 0개다. AI가 헷갈리는 정답 후보 3개를 모두 사실인 것처럼 저장하지 않는다. 실제 분류를 확인·수정하는 주체는 작성자다.

분류 가이드 예시: 카페 겸 서점이라는 경험은 `카페 + 쇼핑`을 제안할 수 있다. 전시까지 했다는 근거가 없으면 ‘문화’를 세 번째로 채우지 않는다. 음식점에서 커피 한 잔을 마셨다고 무조건 카페를 추가하거나, 카페에서 잠깐 글을 썼다는 이유만으로 공부·작업 공간을 자동 추가하지 않도록 기준을 맞춘다.

공원에서 카페로 이동했다는 서술만으로 두 장소의 유형을 한 핀에 모두 붙이지 않는다. 복합 공간 자체를 설명하는지, 여러 장소의 방문 순서를 설명하는지 작성자가 확인한다. 카테고리는 경험별 분류이며 하나의 글로 공통 Place 전체를 덮어쓰지 않는다.

### 9.6 외부 AI 처리와 독립 PRIVATE

직접 LETTER와 직접 PRIVATE 모두 분위기·카테고리 외부 분석을 적용한다. 다른 사용자에게 비공개인 것과 외부 AI에 전송하지 않는 것은 다른 의미라고 안내한다. 자연어 취향을 동률 판단에 전송할 때도 용도를 안내하며 계정 식별정보를 불필요하게 함께 보내지 않는다.

실제 공급자의 학습·보관·외부 처리 계약은 구현 시 확인한다. ‘학습에 쓰지 않음’을 ‘외부 전송·보관 없음’으로 안내하지 않는다. [S4]

LETTER_COPY는 저장된 4축·0~3개 카테고리를 복사하므로 AI 재호출·원문 동기화가 없다. 복사본에 수신자 자신의 취향이나 매칭 점수를 대신 넣지 않는다.

## 10. 이미지 저장과 안전 운영

### 10.1 파일 저장

로컬 파일 시스템에 저장하고 DB에는 서버 저장 루트 기준 상대 경로를 기록한다. 본문에 공개 파일 시스템 경로를 넣지 않고 별도 이미지 조회 API를 사용한다. 이미지가 없으면 `image_path = NULL`이다.

JPG·PNG 이미지 0~1장만 지원한다. JPEG 계열 확장자의 허용 목록, 최대 바이트 수와 해상도는 명세에서 고정한다. 동영상, GIF·SVG·HEIC 등의 추가 형식 및 일반 첨부파일은 이번 지원 대상으로 확장하지 않는다.

파일 확장자와 요청 `Content-Type`만 신뢰하지 않고 실제 형식을 확인한다. 서버 생성 파일명, 크기 제한, 웹 루트 밖 저장과 접근 제어를 적용한다. 이는 OWASP의 업로드 보호 권고에 근거한다. [S1]

사진을 선택했으나 업로드가 실패한 경우를 정상적인 ‘사진 없음’으로 조용히 바꾸지 않는다. 실패를 안내하고 재시도 또는 사진 없이 작성하는 선택을 제공한다. EXIF 등 불필요한 위치·기기 메타데이터 제거와 재인코딩을 권고한다.

### 10.2 사본과 파일 수명

복사 PRIVATE는 새 이미지 경로를 사용한다. 원문 삭제로 원문 파일을 정리해도 PRIVATE 파일은 유지한다. PRIVATE 삭제 시에는 해당 PRIVATE 파일만 정리한다. 원문·사본 파일을 묶는 참조 관리 시스템은 이번 구조에 추가하지 않는다.

배포 환경은 재시작·재배포 후에도 업로드가 남는 저장 공간을 제공해야 한다. 컨테이너를 사용하는 경우 영속 저장 연결을 명세에서 확인한다. 저장 공간 부족·실패 파일 정리·테스트 종료 후 정리 담당자를 지정한다.

### 10.3 배달 전 안전 처리 — 운영 설계 권고

OpenAI Moderation은 텍스트와 이미지 입력을 지원하며, 결과의 `flagged`·범주 점수는 서비스 정책 판단에 사용하는 신호다. API 오류를 안전 판정으로 취급하지 않는다. [S3]

| 상황 | 권고 처리 |
|---|---|
| 안전 검사 완료, 배달 허용 | LETTER 배달 진행 |
| 잠재적 위반 표시 | 배달 보류 후 운영자 확인 또는 명시한 정책으로 반려 |
| 안전 검사 오류·시간 초과 | 내용 보관, 타인 노출 보류, 재시도 가능한 상태 안내 |
| 분위기 태깅만 실패 | 작성자가 4축을 직접 채워야 최종 저장 가능. 근거 없는 강제 추측·미완성 저장 불가 |
| 카테고리 분류만 실패 | Q22 A: 수동·미분류 저장 허용. 안전 실패와 혼동하지 않음 |
| 이미지 검사가 필요한데 검사 실패 | 해당 LETTER를 타인에게 노출하지 않음 |

검토가 필요한 텍스트와 사진은 외부 공개 URL로 만들지 않고 검사한다. Moderation의 이미지 입력은 Base64 데이터 URL도 지원한다. [S3]

### 10.4 신고와 운영

신고는 접수만 하고 끝내지 않는다. 담당자가 신고 목록과 신고된 원문을 확인하고, 배달 중단·원문 숨김·계정 접근 제한 등의 조치를 실행할 최소 수단을 둔다. 별도 완성형 관리자 대시보드가 필수인 것은 아니다.

스팸·개인정보 노출·권리 침해는 API 필터 하나로 모두 판별된다고 주장하지 않는다. 초대 대상 제한, 작성 수 제한, 신고 대응을 함께 사용한다. 사본 일괄 회수가 불가능한 제약과 운영 보완은 16장에서 다룬다.

### 11.1 필수 입력·분류 제약

`UserAtmosphere(user_id, axis_id)`와 `MemoryAtmosphere(memory_id, axis_id)`는 중복되지 않는다. 온보딩 완료 계정과 최종 저장 경험은 지정한 네 축을 모두 갖고 각 값은 -1/+1이다. 분석 응답의 미결은 최종 Memory의 NULL 축으로 저장하지 않는다. 스키마·서비스 검증을 어떻게 분담할지는 BE 계약으로 정한다.

`MemoryCategory(memory_id, category_id)`는 중복되지 않으며 자체 사전에 정의된 값만 0~3개 저장한다. `UNCLASSIFIED / FAILED / CLASSIFIED` 등 분석 상태를 코드 목록과 구분하는 방식을 제안한다. 분류 실패를 OTHER로 자동 변환하지 않는다. source/evidence는 설명용 제안이며 모델의 자체 confidence를 정확도처럼 취급하지 않는다.

### 11.2 일일 배달 제약 — 확정 동작에 따른 구현 제안

사용자별 KST 날짜당 성공 수신은 최대 한 번이며, 동일 원문의 사용자별 재수신도 금지한다. 다음 제약은 목적이 다르므로 함께 반영한다.

| 제약 제안 | 보장하려는 동작 |
|---|---|
| `DailySelection(user_id, service_date)` 유일 | 사용자·날짜별 작업 슬롯 중복 방지 |
| `LetterDelivery(receiver_id, service_date)` 유일 | 원문 삭제·재실행 후에도 그날 두 번째 성공 배달 금지 |
| `LetterDelivery(receiver_id, memory_id)` 유일 | 날짜가 달라도 같은 LETTER를 동일 사용자에게 재배달하지 않음 |

소프트 삭제·원문 일반 삭제로 수신 이력을 함께 지워 날짜별 슬롯을 다시 열지 않는다. 원문과 수신 이력의 삭제·보존 방식 및 로그 보존기간은 별도 기술·운영 계약으로 정한다. 새 수신 확정 직전에 서비스 날짜가 유효한지도 검사한다.

`NO_CANDIDATE`는 정상 종료, `DELIVERED`는 성공 종료, 일시 오류는 당일 재시도 가능 상태로 구분한다. 지난 날짜분 신규 생성은 금지한다. 성공한 수신 기록과 날짜별 작업 상태는 하나의 일관된 확정 단위로 처리하는 안을 권한다. DB 저장 성공 뒤 응답만 유실됐다면 기존 결과를 재사용한다.

실제 `UNIQUE`·트랜잭션·잠금 구성은 BE 계약으로 확정한다. 사용자별 단일 수신 규칙을 전역 원문 단일 소비 규칙으로 확대하지 않는다. 서로 다른 사용자는 같은 LETTER를 각각 받을 수 있다.

### 11.3 독립 보관·파일 제약

`LETTER_COPY`는 PRIVATE만 허용하고 원문 ID·원작성자 ID·원배달 ID·사본 역참조는 저장하지 않는다. `LetterDelivery.liked_at`에는 성공 시각만 기록하며 사본 ID를 두지 않는다. Bookmark 테이블이나 분석 편의용 숨은 사본 연결도 만들지 않는다.

사진과 자연어 설명은 nullable, 본문은 공백만 저장할 수 없다. 복사한 사진은 독립 경로로 보존한다. 공유 Place·분류 사전의 ID는 원문 연결과 다르지만, 원문 삭제가 그 사전이나 독립 PRIVATE를 연쇄 삭제하지 않아야 한다. 복사 당시의 장소·4축·카테고리 표시값을 보존한다.

### 11.4 상태 분리

저장·공개 상태, 안전 검사, 분석 상태, 일일 선정 상태를 하나의 성공/실패로 합치지 않는다. `available_at`은 최초 후보 준비 완료, `delivered_at`은 실제 사용자에게 배달 완료를 의미하도록 제안한다. 분석 중 상태를 FE에서만 관리할지 제한된 임시 분석으로 관리할지는 API 계약으로 정한다.

일일 배달은 매일 09:00, Asia/Seoul 서버 정기 작업이다. GET 조회·필터·새로고침은 선정 트리거가 아니다. 운영·테스트 실행 경로는 일반 사용자에게 열지 않는다. 오늘 상태는 정기 배달 대기·후보 없음·성공·재시도 중·오류 등을 구분해 반환한다. 정시 이후 가입·신규 후보·배달 성공 후 삭제에는 당일 보충하지 않고, 지난 날짜분의 신규 생성도 제공하지 않는다. 재시도는 같은 날의 미완료 오류 작업에만 적용한다.

**분류 계약:** 분석 응답에는 미결 축을 표현할 수 있으나 최종 저장은 네 축이 모두 -1/+1이어야 한다. 잘못된 축·누락·0·소수·중복을 거절한다. 카테고리 0개는 유효하고 4개 이상·외부 사전 코드·중복은 거절한다. 필터에는 코드가 아닌 화면 문자열을 임의 해석해 넣지 않도록 ID 계약을 맞춘다.

**추가 오류 사례:** 선택 설명 없음·삭제, 본문 수정 후 이전 분석 응답, AI 장애 뒤 수동 4축 입력, 미분류와 OTHER, 후보 없음, 고정 1차 동률, 자연어 재동률·오류, 같은 날짜 동시 실행, 배달 컷오프 뒤 신규 등록, 후보 삭제, 이미 받은 원문 재선정, 사본 이미지 복사 실패.

분석 입력은 사용자 본문을 처리하는 데이터이며 임의 명령으로 실행하지 않는다. 매칭 결과에 미선정 후보 본문·작성자 신원을 반환하지 않는다. PRIVATE 편집·좋아요 취소·위치 변경·복사본 재공유 API는 만들지 않는다.

## 13. 개발 방식과 역할·일정

### 13.1 기술 방향

Spring 기반 BE·PostgreSQL·Flyway·로컬 파일 저장·네이버 지도 Web SDK를 유지한다. 네이버 지도 SDK는 좌표·핀 입력을 담당하고 장소 분류는 본문 AI가 담당한다. 업체 검색·역지오코딩을 필수로 추가하지 않는다.

하루 한 편 매칭은 신규 필수 범위다. 4축 점수는 애플리케이션/SQL의 명시적 비교로 구현 가능한 설계이고, 동률의 자연어 비교 방식에 따라 모델 호출 계약을 정한다. pgvector·별도 AI 서버·큐·복잡한 추천 플랫폼을 자동 도입하지 않는다. 모델·키·호환성·배포·저장 지속성은 0~2시간에 계약한다.

### 13.2 유지하는 개발 원칙

**0~2시간에 ERD·API 명세를 문서화하고 FE·BE·AI가 상호 협의하여 확정한다.** 같은 문서·예시로 Mock 테스트를 수행하고, 연결 가능한 기능부터 실제 통합 테스트를 병행한다. 명세 변경은 문서·Mock·구현을 함께 수정한다. 특정 시간의 첫 통합 강제를 추가하지 않는다. Mock 소비자 테스트와 실제 제공자 계약 검증은 구분한다. [S5]

### 13.3 역할 제안

| 담당 | 주요 책임 |
|---|---|
| FE1 | 지도 핀·좌표, 누적 수신함·오늘 상태·필터·읽음 |
| FE2 | 4축 온보딩·설명, 작성·분류 확인, BOOKMARK·내 기록 |
| BE1 | 계정·고정 위치·분류 사전·경험·이미지·권한 |
| BE2 | 일일 선정·배달·중복 방지·좋아요 독립 복사·신고·CI |
| AI | 확정 4축의 추론·근거 부족 응답, 자체 8종의 0~3개 분류, 동률 평가, 안전·실패 계약 |
| 공동 | 후보 시간 규칙·업무 날짜·스키마·입출력·통합·수용 기준 |

### 13.4 19시간 운영안

| 시간 | 작업 |
|---|---|
| 0~2h | 확정 4축·자체 분류·점수·09:00 및 예외 정책을 공통 계약으로 옮기고, 17장의 수치·ERD/API/AI 계약을 상호 합의 |

완성 시간을 보장하는 일정이 아니다. 일일 매칭·필수 4축 확인·복수 카테고리는 실제 작업량이다. 네이버 taxonomy 확보 작업은 자체 8종 채택으로 제거한다. 시간이 부족하면 PUBLIC·댓글·장식 UI를 미루고, 임의로 전체 배달로 되돌리거나 안전·독립 복사를 생략하지 않는다. 실제 배달 시간을 기다리지 않아도 검증할 수 있도록 Clock·테스트 데이터와 제한된 테스트 실행 경로를 제안한다. 이는 운영의 하루 한 편 규칙을 완화하는 기능이 아니다.

### 14.1 시연 순서 제안

수신 계정을 먼저 온보딩한다. 지정된 네 축을 모두 채우고 설명 있는 경우·없는 경우를 준비한다. 이후 같은 1차 점수의 후보 2개, 낮은 1차 점수지만 설명은 유사한 후보, 반경 밖 후보를 새로 작성한다. 자체 카테고리·텍스트만·사진 첨부·미분류·AI 미결 후 수동 4축 입력도 포함한다.

테스트용 Clock을 KST 09:00 전후로 제어하고 정기 실행을 호출하여 최고점 그룹 안의 한 편만 배달되는지 확인한다. 같은 날짜 재실행과 수신함 새로고침으로 추가 배달되지 않아야 한다. 미선정 후보가 다음 날짜에도 남는지, 이미 받은 원문은 제외되는지 확인한다.

수신자는 좋아요·독립 PRIVATE 보관을 수행하고 작성자는 누적 반응 수만 확인한다. 원문 삭제 후 수신 원문은 막히지만 PRIVATE 본문·사진·4축·카테고리는 남아야 한다. 원문 삭제 뒤 같은 날 대체 편지가 생기지 않는지도 확인한다.

제어된 테스트 시계로 날짜를 바꾸고 후보 없음·미접속일·정시 이후 가입·장애 경계를 검사한다. 일반 사용자에게 날짜·할당량 조작 API를 제공하지 않는다. 합성 예시를 실제 경험·실제 이용자의 반응으로 집계하지 않는다. 시연 성공은 실제 추천 품질 증명이 아니다.

## 15. 지표와 사용자 조사

시연 성공은 구현된 계약을 만족하는 것이고 제품 성공은 실제 이용·인터뷰 결과로 확인한다. 현재 사용자 수·정확도·재방문율을 측정했다고 주장하지 않는다.

| 관측 항목 | 목적 |
|---|---|
| 4축 설정 완료·중단 | 필수 4개 입력의 부담 |
| 경험의 축별 근거·사용자 수정 | AI 분위기 오분류·분석 단계 미결·사용자 보완 비율 |
| 카테고리 수정·추가·제거·미분류 | 복수 분류의 품질. 라벨 수 증가를 정확도 증가로 간주하지 않음 |
| 후보 수·최고점·동률 수 | 1차 점수의 구분력과 자연어 단계 빈도 |
| 자연어 평가 실행·실패·fallback | 선택 설명의 실제 사용 기회와 장애 영향 |
| 일일 배달 성공·빈 후보·당일 오류 복구·만료 오류 | 공급 부족과 시스템 실패를 구분. 지난 날짜 오류를 후보 없음으로 집계하지 않음 |
| 원문별 선정 기회·미선정 기간 | 소수 기록 편중·작성자 소외 |
| 카드 실제 노출·상세 열람 | 배달과 실제 소비 분리 |
| 좋아요·복사 성공 | 취소 없는 누적 저장 반응 |
| 작성자 반응 확인·후속 직접 작성 | 피드백과 다음 작성 관계 |
| PRIVATE 재열람·삭제 | 보관의 실제 사용 가치 |

원문·사본 연결 금지를 지킨다. 분석용 숨은 연결키를 만들지 않는다. 사본 재열람은 LETTER_COPY 구분으로 집계하며 원문별 사본 재열람 전환은 측정하지 않는다. 자연어 취향·PRIVATE 본문을 로그에 불필요하게 남기지 않는다.

분류 평가는 확정 4축·자체 8종 사전을 기준으로 사람이 검토한 문장으로 한다. 명확한 근거·무언급·양쪽 혼재·부정 표현·다장소 서술·잘못된 코드·시간 초과를 포함한다. AI 자체 confidence를 실제 정확도로 표현하지 않는다.

불특정 다수 인터뷰에서는 지역 관계·기록 습관·최근 공유 포기 사례·하루 한 편의 수량 선호·선정되지 않은 작성자의 반응을 확인한다. 표본 한계를 기록하며 전체 인구의 대표 결과로 일반화하지 않는다. PUBLIC 재추천의 사업 효과는 별도 후속 가설이다.

## 20. 개발 인계 및 완료 판정

### 20.1 Grilling 종료 범위

### 20.2 구현자가 먼저 읽을 순서
