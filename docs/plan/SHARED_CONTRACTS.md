**병렬 개발의 기준은 구현 완료가 아니라 인터페이스 합의다.** 0~2시간에 위 입력·출력·실패를 먼저 문서화하고, 각 담당자는 상대 포트의 가짜 구현으로 테스트한다. 실제 포트가 준비된 것부터 교체한다.

같은 애플리케이션·같은 DB의 내부 호출을 전제로 한 작업 분리안이다. 사람이 두 명이라는 이유로 별도 서비스/DB나 내부 HTTP 호출을 추가하지 않는다. 새 구조를 현재 코드에 이미 존재하는 것으로 주장하지 않는다.

`BE1 이미지 Controller → BE2 MemoryAccessPolicy → 읽기 Repository`와 `BE2 LikeUseCase → BE1 MemoryStore/LocalImageStore`는 서로 다른 하위 기능이다. 권한 정책이 LikeUseCase를 다시 호출하거나 MemoryStore가 이미지 Controller를 호출하도록 만들지 않아 순환 의존을 피한다. 저장소·DTO가 필요한 최소 인터페이스를 공통 contracts에 두고, 서로의 Controller/서비스 전체를 주입하지 않는다.


## 4. 핵심 통합 트랜잭션

### 4.1 온보딩과 09시 취향 재현 — BE1 주도, BE2 공동 검증

온보딩에서 위치·수신 시작 시각·취향 v1을 함께 확정한다. 설정 수정은 새 불변 버전만 추가한다. BE2는 지연 실행/당일 재시도에서도 예정 cutoff 이전의 실제 설정값을 읽는다. 버전 번호만 남기거나 11시 현재값으로 09시 선정을 복구하지 않는다.

**인계 예:** 08:40 설정 v1, 10:00 v2, 11:00에 09시 실패 복구 → 오늘 작업은 v1, 다음 날은 그날 기준 최신값. 정확히 경계를 가로지르는 미커밋 변경의 처리 방식은 C08/A02/B02의 짧은 쓰기·스케줄 조정 계약으로 명시한다. 타임스탬프 하나로 커밋 시점까지 자동 재현된다고 가정하지 않는다. [S2 §6.1; S1 §6.5.2]

### 4.2 작성→안전 승인→선정 후보 — BE1 주도

A04의 분류 응답은 분석 결과일 뿐이다. A05는 사용자가 완성한 4축과 0~3개 카테고리, 선택 이미지를 검증하여 생성한다. A07의 안전 승인 전에는 `available_at`이 없고 후보에 포함하지 않는다. BE2는 활성 LETTER라고만 조회하지 않고 승인·시간·반경·수신 조건을 함께 적용한다.

**주의:** classification FAILED 후 수동 4축 보완은 저장 가능하지만 moderation ERROR는 배달 가능이 아니다. 직접 PRIVATE도 AI 분류는 하되 후보는 아니다. AI 담당자의 정상 응답이 개인정보/익명/접근 허용까지 결정하지 않는다. [S3 §4; S1 §9~10]

### 4.3 하루 한 편 확정 — BE2 주도

BE2는 일일 슬롯을 선점하고, DB 장기 잠금 없이 B01의 후보/점수/동률 계산을 수행한 뒤 최종 트랜잭션에서 재검사한다. `letter_deliveries` INSERT와 `daily_selections=DELIVERED`를 함께 확정한다. 이미 성공한 슬롯은 삭제·재실행으로 비우지 않는다.

예정 cutoff는 매일 09:00이다. 지연 실행 뒤 신규 계정/후보를 끼워 넣지 않고, 현재 삭제·숨김·계정 제한은 다시 반영한다. 정상 NO_CANDIDATE, 미완료 오류, 과거 날짜 만료를 분리하고 당일 미완료만 복구한다. 다른 수신자가 같은 원문을 받는 것은 허용한다. [S1 §6; S2 §8.3]

### 4.4 좋아요·DB·파일 — BE2가 전체 성공을 책임지고 BE1이 primitive 제공

1. 실제 수신자와 `deliveryId`를 확인한다. 이미 `liked_at`이 있으면 추가 사본 없이 완료 응답한다.
2. 아직 미실행이면 합의한 순서로 원문·수신 행을 잠그고 원문 현재 상태/미실행을 재검사한다.
3. BE1의 파일 기능으로 이미지를 별도 경로에 복사한다. 사진이 없으면 파일 동작 없이 진행한다.
4. BE1의 저장 기능으로 수신자 소유 PRIVATE/LETTER_COPY와 분류를 새로 삽입한다. 원문 식별자는 영구 필드에 넣지 않는다.
5. 같은 DB 트랜잭션에서 `liked_at`을 한 번만 확정한다. 호출된 저장 메서드가 자체 커밋하거나 다른 DB/HTTP 작업으로 분리되지 않아야 한다.
6. 최초 응답의 일회성 `copiedMemoryId`는 API 초안대로 처리하고, 재요청은 `ALREADY_COPIED`와 `null`을 반환한다. 응답 유실 복구를 위해 사본 연결을 캐시에 저장하지 않는다.
7. 파일 실패·DB 롤백·프로세스 중단의 잔여 파일은 BE1 정리 도구를 이용한다. 커밋 여부 불명은 먼저 DB에서 확인하며, 성공 사본 파일을 추정으로 지우지 않는다.

이때 호출 인자에 원문을 잠시 들고 있는 것과, 원문/사본 ID 연결을 DB·파일명·로그에 지속 보관하는 것은 다르다. 전자는 처리상 필요하지만 후자는 금지다. 저장된 원문 내용만 서버에서 복사하며 FE가 사본 본문을 임의 전달해 만드는 API가 아니다. [S2 §8.4; S3 §6.1]

### 4.5 원문 삭제·운영 숨김과 파일 — BE2 주도, BE1 저장/파일 공동

DELETE는 소유자를 확인해 원문 또는 자신의 PRIVATE 한 건만 논리 삭제한다. 원문의 미보관 수신자는 내용/이미지를 더 볼 수 없고, 오늘 슬롯은 DELIVERED로 유지된다. 수신 목록은 내용 없는 안내로 바뀌며 당일 대체는 없다. 독립 PRIVATE의 본문·분류·파일은 건드리지 않는다.

운영 숨김도 사용자 열람/후보 차단에 반영하지만 일반 사용자 삭제와 운영 정책을 혼동하지 않는다. 독립 사본 전체를 원문 ID로 찾아 자동 회수하는 기능은 구현하지 않는다. 사본별 별도 확인·조치 범위는 운영 합의다. [S3 §5~7; S2 §9]
