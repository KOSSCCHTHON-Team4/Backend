# BE1 개별 작업서 — 계정·경험 생성·이미지

- 기준: BE Work Plan 1.0-draft / MVP 1.4-final / API 0.2 / ERD 1.0+인증 보완 v0.2
- 이 문서는 `WORK_PLAN.md`의 동일 작업 ID를 발췌한 인계본이다. 변경은 통합 계획과 함께 반영한다.
- 모든 항목은 앞으로 구현·테스트할 작업이다. 실제 서버/DB에 반영한 상태가 아니다.

- 먼저 `SHARED_CONTRACTS.md`의 포트와 공통 파일 주 담당을 확인한다.

## 담당 작업

### A01. 이메일·비밀번호 인증과 초대 계정 준비

**선행 입력:** C01~C03, S5; 토큰/해시/이메일 정규화/초기 비밀번호 전달 계약  
**산출물:** 인증 서비스, 자격증명 migration/저장소, 내부 계정 준비 명령 또는 승인된 운영 절차, 로그인 테스트

- 로그인에는 email/password만 허용하고 provider/providerToken 혼합·공급자 폴백·자동 회원가입을 구현하지 않는다.
- email_password_credentials에서 이메일 조회키와 password_hash를 관리한다. 원문 비밀번호를 코드·SQL seed·로그에 넣지 않는다.
- 해시 검증 뒤 PENDING/ACTIVE/SUSPENDED/CLOSED를 판정하고 자체 access token을 발급한다. 보호 API에서도 현재 상태를 확인한다.
- 토큰 TTL·갱신 여부는 초안의 합의 항목이다. 이번 작업 기준안은 access token+만료 시 재로그인이고 별도 refresh API를 추가하지 않는다.
- FE 제안인 5회 실패·60초 제한을 서버 계약으로 검토·반영한다. 관찰 구간/초기화/동시성/재시작 유지와 미등록 이메일에도 동일한 제한 키 적용을 정한다.
- 공개 회원가입이 없으므로 테스트 참여자의 최초 계정·해시·초대 상태를 준비하는 도구/절차까지 납품한다.

**완료 기준:** 정상 로그인과 보호 API가 연결되고, 없는 이메일/오입력은 같은 INVALID_CREDENTIALS, 공급자 필드 거절, 앱 재시작으로 실패 제한 우회 불가, 이메일 null·해시 노출 없음.

**협업 경계:** BE2는 Principal/Guard를 소비하고 운영 계정 제한은 A01이 제공하는 계정 상태 변경 서비스로 수행.

### A02. 프로필·온보딩·불변 취향 이력

**선행 입력:** A01, C03, S2의 취향 이력, C08 시간 계약  
**산출물:** User API 3개, 사용자/취향 모델·migration, cutoff 시점 취향 조회 포트

- hasOnboarded를 위치+최초 유효 취향의 일관된 상태에서 파생한다. 온보딩 전 설정값은 명세대로 null이다.
- 최초 위치와 4축·선택 설명의 v1을 한 트랜잭션에 저장한다. 동일한 최초 입력 재전송은 200, 다른 재설정은 409다.
- preferences 수정에는 expectedPreferenceVersion을 검사하고 전체 새 버전을 INSERT한다. 기존 값/위치를 덮어쓰지 않는다.
- preferenceVersion은 revision의 10진 문자열로 반환한다. 본문·계정 설정의 축 누락/0/소수/중복 키를 공통 검증한다.
- BE2에 cutoff 이전 최신 불변 취향의 실제 4축·설명·버전 ID를 제공한다. 버전 번호만 저장하고 값을 지우지 않는다.
- 정확히 09:00을 걸친 미커밋 변경의 적용 규칙과 사용자 행 잠금/유효시각 부여를 B02와 계약한다.

**완료 기준:** 위치 불변, 온보딩 부분 성공 없음, 버전 충돌 409, 08:40 v1→10:00 v2→11:00 복구 시 09:00의 v1을 읽는 테스트.

**협업 경계:** BE2는 버전 테이블에 직접 INSERT/UPDATE하지 않고 조회 포트로 선정용 버전을 얻는다.

### A03. 서비스 설정·4축·8종 카테고리 사전

**선행 입력:** C01·C03; 실제 반경/중심/입력·파일 한도는 팀 합의  
**산출물:** GET /config, /atmosphere-axes, /place-categories, 서버 설정 스키마·seed

- 고정 반경·초기 지도 중심·09:00/Asia/Seoul·인증모드 EMAIL_PASSWORD·제한값을 단일 서버 설정에서 반환한다.
- 반경 1000m 등 mock 숫자를 승인 없이 운영값으로 확정하지 않는다. 필수 설정 누락은 CONFIGURATION_UNAVAILABLE로 다룬다.
- 4축의 정확한 라벨과 -1/+1 대응, 자체 8종 코드·정의·버전을 제공한다. 네이버 업종 사전 수집을 추가하지 않는다.
- AI 분류와 BE2 필터·점수가 같은 코드·버전을 쓰도록 공유 값 객체와 사전 fixture를 제공한다.

**완료 기준:** 온보딩 전 ACTIVE 계정이 세 API를 조회하고 FE/AI/BE에서 동일 사전을 사용. 사용자가 반경을 변경할 수 없음.

**협업 경계:** BE2는 고정 반경을 날짜별 작업 스냅샷에 캡처하며 별도 하드코딩하지 않는다.

### A04. 경험 본문 분석 API와 AI 분류 연동

**선행 입력:** A03, C09, AI 담당자의 분류 스키마·모델 계약  
**산출물:** POST /memories/analyze, 분석 DTO/어댑터·analysisToken 검증 기능, 실패 mock

- 본문으로 분위기 4축과 자체 카테고리 0~3개를 추론하는 AI 모듈을 BE API에 연결한다. 사진/계정 취향으로 빈 축을 추측하지 않는다.
- AI 근거 없음은 축 null로 반환하고 작성자 입력을 요구한다. 카테고리 근거 부족·AI 실패·서버 자체 장애를 구분한다.
- analysisToken 초안을 채택하면 사용자 귀속·본문 대응·결과·서명·만료를 검증한다. 영구 원문-사본 추적 키로 보관하지 않는다.
- 최종 저장값이 AI 제안과 같은지/수정됐는지 서버가 비교하여 AI/USER 출처를 판정한다. 클라이언트의 출처 플래그를 신뢰하지 않는다.
- 본문 수정 뒤 오래된 응답, 만료·변조 확인값, AI 실패 뒤 수동 저장의 NOT_RUN/FAILED 의미를 명세대로 테스트한다.

**완료 기준:** 부분/전체 분석 실패에서도 입력 내용이 유실되지 않고 4축 수동 보완 경로가 동작. 최종 분위기 null은 저장 불가.

**협업 경계:** AI 담당자는 프롬프트/모델/평가 예시를 제공하고, BE1은 인증·API·검증·저장 연결을 끝까지 책임진다.

### A05. 직접 경험 생성과 공용 경험 저장 기능

**선행 입력:** A02~A04, A06; C07 Idempotency, C04 핀 가시성 계약  
**산출물:** POST /memories, Memory/Place/Category 저장소·migration, 독립 PRIVATE 삽입/상태 변경 내부 포트

- 본문·핀 좌표·필수 4축·카테고리 0~3개를 검증하고 memories와 memory_categories를 한 번에 생성한다.
- 클라이언트의 ownerId/originKind/moderationStatus/dataOrigin/source ID는 받지 않는다. 직접 생성은 서버가 DIRECT로 기록한다.
- placeId 미지정 시 새 핀, 지정 시 현재 가시성·좌표 일치를 확인하는 API 초안을 적용한다. 원문 분류로 공통 Place를 덮어쓰지 않는다.
- imageId의 본인 소유·만료·미사용을 검사하고 경험 INSERT와 첨부 소비를 같은 성공 단위로 처리한다.
- C07을 사용해 동일 생성 요청의 응답 유실을 복구한다. 이미 완료한 요청을 확인하기 전에 소비된 이미지/만료된 분석값으로 거절하지 않는다.
- BE2에 원문 잠금·내용 스냅샷·독립 PRIVATE INSERT·일반 삭제/운영 숨김의 하위 저장 기능을 제공한다. 호출자의 트랜잭션에 참여하고 내부에서 별도 커밋하지 않는다.
- LETTER 생성 201은 배달 성공이 아니다. 초기 안전 상태와 available_at은 A07 처리와 일치시킨다.

**완료 기준:** 이미지 없는 직접 LETTER/PRIVATE 정상 생성, 카테고리 상한·4축 제약, 실패 시 부분 생성 없음, 재요청 한 자원, BE2가 외부 HTTP 없이 같은 DB 트랜잭션으로 사본 생성 가능.

**협업 경계:** 스키마·Entity·공용 쓰기 primitive는 BE1, 상세/삭제 API·좋아요 사용사례 orchestration은 BE2. 같은 클래스를 각자 복제하지 않는다.

### A06. 로컬 이미지 업로드·권한 조회·독립 파일 복사

**선행 입력:** C02/C04 권한, C07 Idempotency, 실제 바이트·해상도·만료 계약  
**산출물:** POST /images, GET /memories/{id}/image, image_uploads migration, LocalImageStore, 정리 절차

- JPG/PNG 한 장을 디코딩·형식·바이트·픽셀 검사하고 서버 재인코딩/메타데이터 제거를 적용한다. 미지원 자료는 거절한다.
- 임시 업로드의 owner·STAGED/ATTACHED/EXPIRED·expires_at·첨부 대상을 관리한다. 경로 대신 imageId를 반환한다.
- 경험 사진은 BE2의 공통 가시성 정책 확인 뒤 Bearer API로 반환한다. 정적 공개 디렉터리·서버 경로·토큰 query 노출을 하지 않는다.
- 좋아요용 duplicateIndependent 기능은 별도 무작위 경로와 메타데이터를 반환한다. 원문 ID가 든 사본 경로·공유 원본 파일 참조를 만들지 않는다.
- 미첨부 만료 파일, 롤백 잔여 파일, 원문/PRIVATE의 개별 삭제 후 정리를 구분한다. ATTACHED/진행 중/커밋 여부 불명 파일을 성급하게 지우지 않는다.
- 재배포에도 살아 있는 저장 디렉터리와 운영 용량 점검 절차를 C10 배포 문서에 전달한다.

**완료 기준:** 다른 사용자·만료·이미 첨부한 imageId 거절, 이미지 fetch 권한 테스트, 사진 없는 정상 흐름, 원문 삭제 뒤 사본 사진 보존, 파일·DB 부분 실패 복구 점검.

**협업 경계:** BE1은 파일 기능과 원본/사본 저장 primitive를 제공하고, BE2가 좋아요 전체의 성공/실패 및 DB 커밋을 결정한다.

### A07. 배달 전 안전 검사와 최초 후보 활성화

**선행 입력:** A05~A06, C09, AI 담당자의 안전 검사 결과 계약; PRIVATE 별도 운영 정책  
**산출물:** Moderation 연동·미완료 복구 경로, 최초 available_at 전이, 관리 상태 변경 기능

- 직접 LETTER 본문과 선택 이미지를 검사한다. 검사 전·의심·실패는 일일 후보와 타인 조회에서 제외한다.
- 승인과 최초 available_at을 함께 확정한다. 재시도·운영 상태 변경으로 최초 시각을 신규 글처럼 갱신하지 않는다.
- 분위기/카테고리 실패는 수동 보완 가능하지만 안전 검사 실패는 배달 승인으로 바꾸지 않는다.
- 프로세스 중단으로 PENDING이 영구 잔존하지 않도록 DB의 미완료 상태에 기반한 재시도/운영 처리 경로를 둔다. 별도 외부 큐는 필수로 추가하지 않는다.
- 직접 PRIVATE의 AI 분류는 유지하되 moderation 범위는 D09 운영 합의에 맞춘다. 분류 대상이라는 이유로 PRIVATE를 배달하지 않는다.
- BE2 신고 운영 도구에서 호출할 원문 숨김·후보 차단 기능을 제공한다. 상태 전이를 계정/경험 수정 API로 우회하지 않는다.

**완료 기준:** 승인 전 타인 노출/매칭 불가, 오류 뒤 재처리 가능, available_at 최초값 보존, 09시 뒤 신규 승인 글은 오늘 복구 후보에 들어오지 않음.

**협업 경계:** AI는 판정 결과를 제공, BE1은 저장·공개 가능 상태, BE2는 후보 검사와 신고 사용사례를 책임진다.

**병렬 개발의 기준은 구현 완료가 아니라 인터페이스 합의다.** 0~2시간에 위 입력·출력·실패를 먼저 문서화하고, 각 담당자는 상대 포트의 가짜 구현으로 테스트한다. 실제 포트가 준비된 것부터 교체한다.

같은 애플리케이션·같은 DB의 내부 호출을 전제로 한 작업 분리안이다. 사람이 두 명이라는 이유로 별도 서비스/DB나 내부 HTTP 호출을 추가하지 않는다. 새 구조를 현재 코드에 이미 존재하는 것으로 주장하지 않는다.

`BE1 이미지 Controller → BE2 MemoryAccessPolicy → 읽기 Repository`와 `BE2 LikeUseCase → BE1 MemoryStore/LocalImageStore`는 서로 다른 하위 기능이다. 권한 정책이 LikeUseCase를 다시 호출하거나 MemoryStore가 이미지 Controller를 호출하도록 만들지 않아 순환 의존을 피한다. 저장소·DTO가 필요한 최소 인터페이스를 공통 contracts에 두고, 서로의 Controller/서비스 전체를 주입하지 않는다.

## 완료 보고

각 작업 ID에 구현 상태, migration/계약 변경, 실제 실행한 테스트, 미실행 테스트, 상대 BE/FE/AI 인계와 잔여 설정을 적는다. `TEST_OWNERSHIP.md`의 본인 주 담당 시나리오와 통합 계획 I01~I22를 함께 확인한다.

같은 Memory 테이블을 쓴다는 이유로 source_memory_id 또는 사본 응답 캐시를 추가하지 않는다. 모델 주 담당과 use case 주 담당을 구분하고, 단일 DB 트랜잭션이 필요한 좋아요·일일 수신 확정은 서로 다른 HTTP 호출/독립 커밋으로 나누지 않는다.
