로그인은 이미 **이메일+비밀번호만**으로 확정됐다. 공급자 로그인 선택을 다시 열지 않는다. S2에 남아 있는 provider/subject는 현재 구현 경로가 아니다. API 초안의 analysisToken·Idempotency-Key·최초 사본 ID·임시 업로드·신고 코드 등은 **이 계획의 구현 기준안**으로 배정하지만, 사용자가 각각을 별도로 최종 승인했다고 표현하지 않는다. D01~D09 계약을 팀이 확정한 뒤 해당 범위를 구현한다. [S3 §1·§14; S5 §1~5]

### 1.2 백엔드 구현 범위

22개 참여자 API뿐 아니라 최초 초대 계정 준비, 안전 검사·후보 활성화, 09시 정기 선정, 일일 중복/오류 복구, 임시 이미지 정리, 공통 요청 중복 방지, 신고 운영 도구, 마이그레이션·실DB 테스트·배포 설정을 포함한다. 공개 API가 없다는 이유로 이런 작업을 누락하지 않는다. [S1 §6·§10·§13; S3 §11]

이번에는 공개 회원가입·공급자 인증·비밀번호 재설정/변경 API·위치 변경·PRIVATE 편집·좋아요 취소·복사본 재공유·푸시/자동 폴링을 추가하지 않는다. PUBLIC·댓글은 핵심 완료 뒤 후순위, PUBLIC 정기 재추천은 구현 제외다. refresh는 기존 무갱신 제안 기준으로 범위 밖에 두고 별도 채택 시 계약을 다시 작성한다. PostGIS·pgvector·별도 큐·마이크로서비스를 미리 필수화하지 않는다.

### 1.3 유지할 제품 규칙

- 계정/최종 경험의 정확한 4축은 모두 -1/+1 필수다. AI가 모르면 작성자가 보완한다. 카테고리는 자체 8종 중 0~3개다.
- 매일 **09:00 Asia/Seoul**, 온보딩 이후 적격 미수신 후보 중 4축 일치 개수(0~4) 우선, 최고점 동률에만 선택 자연어, 남은 동률/실패는 최고점 범위의 무작위다.
- 후보 없음·정시 뒤 가입/새 후보·성공 뒤 원문 삭제는 당일 보충하지 않는다. 당일 오류만 재시도하고 지난 날짜분은 새로 만들지 않는다.
- LIKE는 한 번의 PRIVATE 독립 복사다. 원문·원작성자·배달 ID와 사본을 지속 연결하지 않으며 원문 일반 삭제가 사본을 지우지 않는다.
- 실제 수신/소유 권한과 익명을 목록·핀·개수·상세·이미지까지 지킨다. 필터는 조회만 바꾸고 수신을 생성하지 않는다.

이 규칙은 S1 §3·§6~9의 유지 사항이다. 아래 역할 배정은 기능 변경이 아니라 그 규칙을 누가 구현·검증할지에 관한 제안이다.

## 2. 역할 요약과 작업 경계

| 구분 | BE1 — 계정·생성·파일 | BE2 — 선정·수신·보관·조회 |
|---|---|---|
| 사용자에게 제공할 흐름 | 로그인 → 온보딩 → 분석 → 직접 경험/이미지 저장 → 배달 준비 | 적격 후보 → 하루 한 편 → 읽기 → 좋아요 독립 보관 → 조회·신고 |
| 주 API | 인증/설정/사용자/분류/직접 생성/이미지 11개 | 수신/좋아요/보관/상세·삭제/지도/신고 11개 |
| 비API 핵심 | 계정 준비, 안전 검사, available_at 활성화, 파일 정리 | 서버 정기 작업, 작업 복구, 운영 신고 처리 |
| 데이터 주 소유 | 계정·자격증명·취향·장소·경험·분류·임시 이미지 | 일일 작업·수신·신고·공통 생성 재시도 저장 |
| 위험 집중 구간 | 인증, 미완료 이미지, AI-사용자 값 구분, 원문 수명 | 시간·동시성, 접근 제어, 사본 생성·일일 배달 원자성 |

**11개씩이라는 숫자가 동일한 공수를 뜻하지는 않는다.** BE1에는 인증/이미지/AI 연결이, BE2에는 매칭·조회·동시성/사본 orchestration이 몰려 있다. 공통 C07/C10을 BE2가, 경험 저장·파일 primitive를 BE1이 맡아 중복과 의존 대기를 줄인다. 담당자의 숙련도·기존 구현 상태는 확인하지 않았으므로 이 표는 능력 평가나 완료 시간 보장이 아니다.

### 2.1 동일한 경험 테이블을 둘 다 사용하는 원칙

BE1은 `Memory`/`Place` 모델과 원자적 저장·상태 변경의 하위 기능을 관리한다. BE2는 읽기 projection·접근 정책 및 **상세/삭제/좋아요 사용사례**를 구현한다. BE2가 모델을 변경해야 하면 BE1 리뷰를 거친다. 모델을 둘로 복사하거나, 코드 소유권을 이유로 같은 DB 트랜잭션을 별도 HTTP 요청으로 쪼개지 않는다.

`POST /memories`와 `DELETE /memories/{id}`의 Controller가 다른 담당이어도 문제없다. 예를 들어 생성/조회/삭제 Controller 파일을 분리하고 동일 공통 모델을 참조한다. 삭제/좋아요의 최종 상태는 같은 저장 primitive와 잠금 순서를 사용한다.

## 4. BE1 상세 작업

인증·기본 설정을 먼저 제공하고, 상대 구현을 기다리지 않도록 모델/포트·mock부터 만든다. 다음 모든 기능은 범위 안에 있으며 순서는 착수 의존성을 뜻한다. [S3 §3~4; S5]

### A01. 이메일·비밀번호 인증과 초대 계정 준비

**선행 입력:** C01~C03, S5; 토큰/해시/이메일 정규화/초기 비밀번호 전달 계약  
**산출물:** 인증 서비스, 자격증명 migration/저장소, 내부 계정 준비 명령 또는 승인된 운영 절차, 로그인 테스트

- 로그인에는 email/password만 허용하고 provider/providerToken 혼합·공급자 폴백·자동 회원가입을 구현하지 않는다.
- email_password_credentials에서 이메일 조회키와 password_hash를 관리한다. 원문 비밀번호를 코드·SQL seed·로그에 넣지 않는다.
- 해시 검증 뒤 PENDING/ACTIVE/SUSPENDED/CLOSED를 판정하고 자체 access token을 발급한다. 보호 API에서도 현재 상태를 확인한다.
- 토큰 TTL·갱신 여부는 초안의 합의 항목이다. 이번 작업 기준안은 access token+만료 시 재로그인이고 별도 refresh API를 추가하지 않는다.
- FE 제안인 5회 실패·60초 제한을 서버 계약으로 검토·반영한다. 관찰 구간/초기화/동시성/재시작 유지와 미등록 이메일에도 동일한 제한 키 적용을 정한다.
- 공개 회원가입이 없으므로 테스트 참여자의 최초 계정·해시·초대 상태를 준비하는 도구/절차까지 납품한다.

**완료 기준:** 정상 로그인과 보호 API가 연결되고, 없는 이메일/오입력은 같은 INVALID_CREDENTIALS, 공급자 필드 거절, 앱 재시작으로 실패 제한 우회 불가, 이메일 null·해시 노출 없음.

**협업 경계:** BE2는 Principal/Guard를 소비하고 운영 계정 제한은 A01이 제공하는 계정 상태 변경 서비스로 수행.

### A02. 프로필·온보딩·불변 취향 이력

**선행 입력:** A01, C03, S2의 취향 이력, C08 시간 계약  
**산출물:** User API 3개, 사용자/취향 모델·migration, cutoff 시점 취향 조회 포트

- hasOnboarded를 위치+최초 유효 취향의 일관된 상태에서 파생한다. 온보딩 전 설정값은 명세대로 null이다.
- 최초 위치와 4축·선택 설명의 v1을 한 트랜잭션에 저장한다. 동일한 최초 입력 재전송은 200, 다른 재설정은 409다.
- preferences 수정에는 expectedPreferenceVersion을 검사하고 전체 새 버전을 INSERT한다. 기존 값/위치를 덮어쓰지 않는다.
- preferenceVersion은 revision의 10진 문자열로 반환한다. 본문·계정 설정의 축 누락/0/소수/중복 키를 공통 검증한다.
- BE2에 cutoff 이전 최신 불변 취향의 실제 4축·설명·버전 ID를 제공한다. 버전 번호만 저장하고 값을 지우지 않는다.
- 정확히 09:00을 걸친 미커밋 변경의 적용 규칙과 사용자 행 잠금/유효시각 부여를 B02와 계약한다.

**완료 기준:** 위치 불변, 온보딩 부분 성공 없음, 버전 충돌 409, 08:40 v1→10:00 v2→11:00 복구 시 09:00의 v1을 읽는 테스트.

**협업 경계:** BE2는 버전 테이블에 직접 INSERT/UPDATE하지 않고 조회 포트로 선정용 버전을 얻는다.

## 5. BE2 상세 작업

공통 읽기 정책·커서·Idempotency와 순수 매칭 함수를 먼저 만들고, 고정된 계정·후보 fixture로 개발한다. 실제 계정/경험 저장이 준비되면 포트를 교체한다. [S1 §6~8; S2 §8; S3 §5~7]

### B01. 후보 조회·4축 점수·동률 해소

**선행 입력:** A02 시점 취향, A03 사전/반경, A05/A07 후보 데이터 계약, C08/C09  
**산출물:** 후보 읽기 쿼리, 순수 점수 함수, 자연어 동률 조합·검증·무작위 대체, 단위 테스트

- 온보딩 이후 available_at, 해당 날짜 09:00 cutoff, 반경, 초대·현재 권한, 안전 승인, 타인 LETTER, 미수신 여부를 먼저 검사한다.
- 4축 동일 가중치로 일치 개수 0~4점을 계산한다. 카테고리를 수신 제외·가산점으로 넣지 않는다.
- 최고점이 하나면 그대로 선택하고 동률일 때만 선택 자연어를 비교한다. 1차 하위 점수 후보를 자연어로 승격시키지 않는다.
- 설명 없음·무효 결과·모델 오류·최종 동률에는 최고점 범위 내 무작위 규칙을 적용한다. 유효한 자연어 공동1위 처리도 계약한다.
- 미수신 후보는 다음 날에도 남기되 같은 원문을 같은 사용자에게 두 번 보내지 않는다. 원문을 전역에서 소모하지 않는다.
- 모델에 제공하지 않은 ID·하위 점수 ID·권한 없는 ID를 검증하고, 미선정 후보 본문/개수를 사용자 응답에 노출하지 않는다.

**완료 기준:** 16×16 점수 조합, 단독/동률/자연어 실패, 시간·반경·자기 글·중복 제외, 같은 글을 두 사용자에게 각각 전달 가능한 테스트.

**협업 경계:** AI 담당자는 동률 판단 모듈, BE1은 어댑터, BE2는 후보 범위·우선순위·최종 선택을 소유한다.

### B02. 매일 09:00 배달 작업·재시도·일일 슬롯

**선행 입력:** B01, A02 불변 취향, C05/C08, 계정 상태·원문 최종 재검사 포트  
**산출물:** daily_selections/letter_deliveries migration, 서버 스케줄 작업, 선점·복구·날짜 경계 테스트

- 09시 시점의 실제 취향 버전과 반경을 참조/캡처한다. 지연된 첫 실행에도 과거 설정을 재현하고 버전 번호만으로 재현됐다고 처리하지 않는다.

- 서비스 날짜별 단일 작업·단일 성공 수신, 사용자별 동일 원문 재수신 금지를 각각 DB 제약과 서비스 테스트로 검사한다.

**완료 기준:** 컷오프·미접속일·중복 worker·당일 장애·자정 지연·후보 없음·삭제 후 대체 금지 시나리오 통과. GET 요청이 배달을 실행하지 않음.

**협업 경계:** BE1의 계정/원문 변경과 같은 잠금·시각 계약을 사용한다. 개발 중 고정 후보·프로필 fixture로 독립 테스트 가능.

### B03. 오늘 상태·누적 수신함·읽음

**선행 입력:** B02 테이블/fixture, C04/C06/C08

**완료 기준:** 정시 전/첫 배달 내일/처리 지연/후보 없음/장애/삭제의 FE 응답 fixture, 커서 변조·필터 변경·한 축 양쪽 필터, 최초 읽음 보존 테스트.

**협업 경계:** B02 완료 전에도 일일 상태·수신 fixture로 FE 화면을 연결할 수 있다. 운영에서는 저장된 실제 상태만 읽는다.

**산출물:** POST like, 한 번의 DB 확정 use case, 이미지 실패·경합 회귀 테스트

- 인증된 실제 수신자인지 먼저 검사한다. 이미 liked_at이 있으면 원문/사본 삭제와 무관하게 200 ALREADY_COPIED로 반환한다.
- 미실행이고 원문이 무효면 410. 유효하면 원문→수신 행 등 합의한 순서로 잠그고 미실행 여부를 다시 확인한다.
- 새 PRIVATE/DIRECT가 아니라 PRIVATE/LETTER_COPY를 생성한다. 본문·장소·4축·분류·dataOrigin을 복사하고 새로운 소유자를 수신자로 설정한다.
- BE1의 파일 복사 기능으로 별도 파일을 만들고, 새 PRIVATE·카테고리 INSERT와 liked_at을 같은 DB 트랜잭션으로 확정한다.
- 원문/배달/원작성자/이미지 원본 연결·역참조·원문+사본 응답 로그를 남기지 않는다. C07 범용 캐시를 적용하지 않는다.
- API 초안에 따라 최초 응답에만 copiedMemoryId를 일회성으로 반환하고 재요청에는 null이다. 사본 삭제 뒤 같은 편지 재복사는 불가하다.
- 파일·DB 실패와 응답 유실을 구분해 재시도/정리한다. 커밋 여부 불명 상태에서 성공한 사본 파일을 지우지 않는다.

**완료 기준:** 동시/반복/응답 유실 요청에서 사본 한 개, 파일 실패 뒤 재시도, 원문 삭제 뒤 사본 보존, 이미 실행 후 원문 삭제 재요청 완료 응답, 지속 연결 없음.

**협업 경계:** BE2가 전체 트랜잭션 주 담당이다. BE1의 하위 쓰기/파일 메서드는 같은 호출 내 기능 제공이며 독립 DB 커밋·HTTP 호출로 분리하지 않는다.

### B05. 경험 상세·삭제·보관함·내 기록·지도 조회

**선행 입력:** C04/C06, A05 모델·쓰기 primitive, A06 파일 수명, B02 수신·B04 반응  
**산출물:** 조회/삭제 API 6개, 공통 권한 정책·익명 DTO·읽기 projection, 지도 bbox/보관함 테스트

- BOOKMARK는 본인 PRIVATE+ACTIVE 조회로 구현한다. source 원문을 JOIN하지 않고 DIRECT/LETTER_COPY를 구분한다.
- 경험 상세는 작성자/소유자/실제 수신자에 따라 필드를 투영한다. Entity 전체를 직렬화하지 않으며 원작성자 신원을 수신 응답에 넣지 않는다.
- 본인 일반 삭제는 첫/반복 모두 204, 타인 삭제는 404다. B04 및 B02와 잠금 순서를 맞추고 원문/사본/수신·좋아요 이력을 같이 지우지 않는다.
- 내 보낸 LETTER의 누적 좋아요 수만 제공한다. 반응자 목록이나 복사본의 현재 수량을 반응 수로 사용하지 않는다.
- bbox=서경도,남위도,동경도,북위도로 가시 핀만 조회한다. memoryCount/분류 집계는 현재 사용자 권한 범위에서 계산한다.
- 자동 근접 좌표 병합·네이버 상호 추측·무권한 핀 반환을 하지 않는다. 장소별 목록은 같은 정책과 커서로 조회한다.
- C04의 동일 정책을 BE1 이미지 API와 핀 재사용 검사에 제공한다. 이 모듈은 B04를 호출하는 것이 아니라 수신 읽기 포트를 사용한다.

**완료 기준:** 미수신/타인 PRIVATE의 상세·핀·개수·이미지 누출 없음, 반복 삭제 204, 삭제 후 일일 슬롯 유지, 독립 보관함 원문 미참조, 범위·페이지 테스트.

**협업 경계:** Memory/Place 모델 주 소유는 BE1, 읽기 query/DTO 및 삭제 use case 주 소유는 BE2. 스키마 변경은 교차 리뷰한다.

### B06. 신고 접수와 최소 운영 처리

**선행 입력:** C04/C07, A01 계정 상태 변경 포트, A07 원문 숨김 포트; 신고 코드/운영자 정책  
**산출물:** POST /reports, reports.details migration, 제한된 운영 명령/내부 도구, 처리 기록·운영 runbook

- 현재 열람 가능한 경험만 신고하고 reason 코드·선택 details를 검증한다. 동일 제출 재요청은 C07으로 같은 접수증을 반환한다.
- 신고 접수 성공을 즉시 콘텐츠 차단 완료로 표현하지 않는다. 새 신고 자체를 임의 UNIQUE로 금지하지 않는다.
- 운영자가 OPEN/IN_REVIEW/RESOLVED/DISMISSED를 처리하고 담당자/시각/내부 메모를 기록할 최소 도구를 제공한다.
- 제한된 CLI 또는 별도 내부 API 중 합의한 하나로 원문 숨김·후보 차단·계정 제한을 실행한다. 공개 참여자용 22 API와 분리하며 일반 계정에 노출하지 않는다.
- 원문 ID로 사본 전체를 찾는 기능은 만들지 않는다. 별도로 확인된 PRIVATE 조치는 고지·권한·보존 계약에 따른다.
- 운영 조치 이후 상세·이미지·후보·수신 상태가 일관되게 차단되는지 BE1과 확인한다.

**완료 기준:** 신고→운영 조회→원문 숨김/계정 제한→다음 API/배달 차단의 실제 경로 확인. 신고만 저장하고 처리 담당 없는 상태로 완료 처리하지 않음.

**협업 경계:** 운영 도구는 BE2, 계정 제한/콘텐츠 상태의 하위 쓰기 구현은 해당 모델 소유자 BE1과 협력한다.

### 6.2 두 사람이 반드시 함께 확인할 항목

공통 구현 완료와 공동 검증은 다르다. 온보딩→첫 후보, 09시 취향 시점 재현, 실제 배달 이후의 이미지 권한, 좋아요의 DB+파일 부분 실패, 원문 삭제와 좋아요 경합, 계정 제한과 배달 경합, 신규 migration 전체 적용은 양쪽 담당자가 함께 확인한다.

공통 enum/DTO/오류 코드 변경은 OpenAPI→BE DTO→FE mock/Zod→fixture를 같은 변경 단위로 갱신한다. 한쪽만 새 필드를 사용하는 상태를 정상 연동으로 표시하지 않는다. [S3 §12.3]

### 7.1 migration 협업

BE1은 migration 번호/적용 순서 목록을 관리하고, 각 담당자는 자기 테이블의 migration을 별도 파일로 작성한다. 공유된 기존 V1/V2가 실제 DB에 적용됐는지 먼저 확인한다. 적용된 파일을 덮어쓰거나 `auth_identities`를 무조건 DROP하지 않는다. 초기 빈 DB라면 이메일 자격증명 기준의 초기 스키마를 별도 검토할 수 있다.

BE2는 모든 migration을 합친 새 테스트 DB 적용을 C10에서 실행한다. 서로 다른 버전의 Schema/Entity로 mock만 맞추지 않도록 코드와 migration을 함께 리뷰한다. 임시 이미지와 직접 생성의 연결은 원문-사본 연결이 아니지만, like에서 `source_image_id`나 응답 캐시로 원문-사본을 다시 잇지는 않는다.

### 7.2 반드시 유지할 DB·서비스 불변조건

| 조건 | 구현 주 담당 | 검증 상대 |
|---|---|---|
| 최종 4축 -1/+1 전부 존재, 카테고리 중복 없음·0~3 슬롯 | BE1 | BE2 |
| 계정당 이메일 조회키 유일, 위치 최초 설정 후 불변 | BE1 | BE2 |
| 취향 전체값의 불변 버전, 일일 버전 소유자 일치 | BE1(이력) / BE2(참조) | 공동 |
| 사용자·날짜 작업 PK, 사용자·날짜 수신 UNIQUE, 사용자·원문 수신 UNIQUE | BE2 | BE1 |
| 원문 상태·파일 삭제가 이미 저장된 PRIVATE와 성공 수신 이력을 지우지 않음 | BE1(저장/파일) / BE2(사용사례) | 공동 |

| 원문·핀·카테고리 집계·이미지의 접근 권한 일치 | BE2 정책 / BE1 이미지 적용 | 공동 |

| UserContext / AccountAccessReader | BE1 | BE2 | 로그인 사용자의 내부 ID, 접근 상태·수신 시작·고정 위치 | 브라우저의 userId를 신뢰하지 않음; 계정 제한은 현재값 재확인 |
| PreferenceHistoryReader.findAt | BE1 | BE2 | userId+cutoff → 불변 버전 ID·revision·4축·선택 설명 | 오전 기준을 복구 시점 최신값으로 대체하지 않음 |
| MemoryStore / MemoryLifecyclePort | BE1 | BE2 | 원문 잠금·스냅샷 읽기, PRIVATE 및 분류 INSERT, 본인 삭제/운영 숨김의 내부 쓰기 | 호출자 DB 트랜잭션 참여, 별도 커밋 금지; source ID를 저장값에 넣지 않음 |
| LocalImageStore | BE1 | BE2 | 검증된 메타데이터, 독립 파일 복사·제한된 삭제/정리 | 원문과 다른 경로; 커밋 여부 불명 파일은 즉시 삭제하지 않음 |
| MemoryAccessPolicy + DeliveryReadPort | BE2 | BE1 | actor+memory/action → 실제 열람·이미지·핀 재사용 가능 여부/오류 분류 | 반경 안=읽기 가능 아님. 배달 읽기 query 사용; like use case 호출 금지 |
| IdempotencyExecutor | BE2 | BE1/B06 | actor+method+path+key+fingerprint → 실행권/기존 결과/충돌 | 자원 INSERT와 완료 기록 원자적 확정. like 응답 저장·사본 연결 금지 |
| SignedValueCodec / ContractError | BE1 | BE2 | 분석 확인값/커서에 쓸 서명·검증 수단과 공통 오류 형식 | 용도·사용자·버전/만료를 구분; 인증토큰/분석토큰/커서를 상호 재사용 불가하게 계약 |
| AnalysisPort / ModerationPort | AI 담당자+BE1 어댑터 | BE1 | 본문·사전 / 본문·선택이미지 → 분류/안전 결과 | 안전 실패와 분류 실패는 다름. AI가 DB·수신 이력에 직접 쓰지 않음 |
| PreferenceTieBreakPort | AI 담당자+BE1 어댑터 | BE2 | 최고점 동률 후보+선택 설명 → 제공한 ID의 순위 또는 평가 실패 | 최종 최고점 범위 검사·오류 무작위 처리는 BE2 책임 |
| ServiceClock / DistancePolicy | BE2 | BE1 | KST 서비스 날짜/예정 cutoff, 좌표→미터 거리 | 고정 반경값은 A03에서 읽음. 테스트 시계는 테스트 환경에서만 제어 |

**병렬 개발의 기준은 구현 완료가 아니라 인터페이스 합의다.** 0~2시간에 위 입력·출력·실패를 먼저 문서화하고, 각 담당자는 상대 포트의 가짜 구현으로 테스트한다. 실제 포트가 준비된 것부터 교체한다.

같은 애플리케이션·같은 DB의 내부 호출을 전제로 한 작업 분리안이다. 사람이 두 명이라는 이유로 별도 서비스/DB나 내부 HTTP 호출을 추가하지 않는다. 새 구조를 현재 코드에 이미 존재하는 것으로 주장하지 않는다.

`BE1 이미지 Controller → BE2 MemoryAccessPolicy → 읽기 Repository`와 `BE2 LikeUseCase → BE1 MemoryStore/LocalImageStore`는 서로 다른 하위 기능이다. 권한 정책이 LikeUseCase를 다시 호출하거나 MemoryStore가 이미지 Controller를 호출하도록 만들지 않아 순환 의존을 피한다. 저장소·DTO가 필요한 최소 인터페이스를 공통 contracts에 두고, 서로의 Controller/서비스 전체를 주입하지 않는다.

## 9. 핵심 통합 트랜잭션

### 9.1 온보딩과 09시 취향 재현 — BE1 주도, BE2 공동 검증

온보딩에서 위치·수신 시작 시각·취향 v1을 함께 확정한다. 설정 수정은 새 불변 버전만 추가한다. BE2는 지연 실행/당일 재시도에서도 예정 cutoff 이전의 실제 설정값을 읽는다. 버전 번호만 남기거나 11시 현재값으로 09시 선정을 복구하지 않는다.

**인계 예:** 08:40 설정 v1, 10:00 v2, 11:00에 09시 실패 복구 → 오늘 작업은 v1, 다음 날은 그날 기준 최신값. 정확히 경계를 가로지르는 미커밋 변경의 처리 방식은 C08/A02/B02의 짧은 쓰기·스케줄 조정 계약으로 명시한다. 타임스탬프 하나로 커밋 시점까지 자동 재현된다고 가정하지 않는다. [S2 §6.1; S1 §6.5.2]

### 9.2 작성→안전 승인→선정 후보 — BE1 주도

A04의 분류 응답은 분석 결과일 뿐이다. A05는 사용자가 완성한 4축과 0~3개 카테고리, 선택 이미지를 검증하여 생성한다. A07의 안전 승인 전에는 `available_at`이 없고 후보에 포함하지 않는다. BE2는 활성 LETTER라고만 조회하지 않고 승인·시간·반경·수신 조건을 함께 적용한다.

**주의:** classification FAILED 후 수동 4축 보완은 저장 가능하지만 moderation ERROR는 배달 가능이 아니다. 직접 PRIVATE도 AI 분류는 하되 후보는 아니다. AI 담당자의 정상 응답이 개인정보/익명/접근 허용까지 결정하지 않는다. [S3 §4; S1 §9~10]

### 9.3 하루 한 편 확정 — BE2 주도

BE2는 일일 슬롯을 선점하고, DB 장기 잠금 없이 B01의 후보/점수/동률 계산을 수행한 뒤 최종 트랜잭션에서 재검사한다. `letter_deliveries` INSERT와 `daily_selections=DELIVERED`를 함께 확정한다. 이미 성공한 슬롯은 삭제·재실행으로 비우지 않는다.

예정 cutoff는 매일 09:00이다. 지연 실행 뒤 신규 계정/후보를 끼워 넣지 않고, 현재 삭제·숨김·계정 제한은 다시 반영한다. 정상 NO_CANDIDATE, 미완료 오류, 과거 날짜 만료를 분리하고 당일 미완료만 복구한다. 다른 수신자가 같은 원문을 받는 것은 허용한다. [S1 §6; S2 §8.3]

### 9.4 좋아요·DB·파일 — BE2가 전체 성공을 책임지고 BE1이 primitive 제공

1. 실제 수신자와 `deliveryId`를 확인한다. 이미 `liked_at`이 있으면 추가 사본 없이 완료 응답한다.
2. 아직 미실행이면 합의한 순서로 원문·수신 행을 잠그고 원문 현재 상태/미실행을 재검사한다.
3. BE1의 파일 기능으로 이미지를 별도 경로에 복사한다. 사진이 없으면 파일 동작 없이 진행한다.
4. BE1의 저장 기능으로 수신자 소유 PRIVATE/LETTER_COPY와 분류를 새로 삽입한다. 원문 식별자는 영구 필드에 넣지 않는다.
5. 같은 DB 트랜잭션에서 `liked_at`을 한 번만 확정한다. 호출된 저장 메서드가 자체 커밋하거나 다른 DB/HTTP 작업으로 분리되지 않아야 한다.
6. 최초 응답의 일회성 `copiedMemoryId`는 API 초안대로 처리하고, 재요청은 `ALREADY_COPIED`와 `null`을 반환한다. 응답 유실 복구를 위해 사본 연결을 캐시에 저장하지 않는다.
7. 파일 실패·DB 롤백·프로세스 중단의 잔여 파일은 BE1 정리 도구를 이용한다. 커밋 여부 불명은 먼저 DB에서 확인하며, 성공 사본 파일을 추정으로 지우지 않는다.

이때 호출 인자에 원문을 잠시 들고 있는 것과, 원문/사본 ID 연결을 DB·파일명·로그에 지속 보관하는 것은 다르다. 전자는 처리상 필요하지만 후자는 금지다. 저장된 원문 내용만 서버에서 복사하며 FE가 사본 본문을 임의 전달해 만드는 API가 아니다. [S2 §8.4; S3 §6.1]

### 9.5 원문 삭제·운영 숨김과 파일 — BE2 주도, BE1 저장/파일 공동

DELETE는 소유자를 확인해 원문 또는 자신의 PRIVATE 한 건만 논리 삭제한다. 원문의 미보관 수신자는 내용/이미지를 더 볼 수 없고, 오늘 슬롯은 DELIVERED로 유지된다. 수신 목록은 내용 없는 안내로 바뀌며 당일 대체는 없다. 독립 PRIVATE의 본문·분류·파일은 건드리지 않는다.

운영 숨김도 사용자 열람/후보 차단에 반영하지만 일반 사용자 삭제와 운영 정책을 혼동하지 않는다. 독립 사본 전체를 원문 ID로 찾아 자동 회수하는 기능은 구현하지 않는다. 사본별 별도 확인·조치 범위는 운영 합의다. [S3 §5~7; S2 §9]

| 자연어 동률 | 제공된 최고점 후보의 비교 결과 | 공통 AI 호출 어댑터·비밀값·오류 계약 | 후보 제공·하위 점수 배제·유효 ID 검사·무작위 대체 |
| 실패·테스트 | 정상/미결/실패/무효 예시 | 서버 실패 상태와 저장 연결 | 매칭 규칙·일일 수신량 보호 |

AI 담당자가 없거나 결과물이 늦는 경우에도 BE 각자는 가짜 포트로 개발할 수 있다. 다만 실제 AI 기능을 구현/검증한 것으로 보고하거나 확정된 자연어 동률 기능을 조용히 삭제하지 않는다. AI 담당자가 DB/수신 이력을 직접 쓰도록 책임을 넘기지 않는다.

## 11. 테스트와 완료 기준

### 11.1 개별 작업 완료의 공통 정의

각 작업은 Controller 작성만으로 완료하지 않는다. **계약/도메인 검증 → 정상·오류·권한 테스트 → 필요한 DB/파일 검사 → 실제 FE 교체 또는 계약 fixture 대조 → 문서 갱신·교차 리뷰**까지 수행하고 결과를 남긴다.

테스트 상태는 `미착수 / 개발 중 / 개별 테스트 완료 / 상대 모듈 연동 완료 / FE 연동 완료`로 구분하는 것을 제안한다. 실행하지 않은 항목을 ‘예시 정상’만으로 통과 처리하지 않는다.

## 13. 인계·변경 관리

### 13.1 저장소 작업 경계 제안

아래는 실제 저장소에 이미 있는 구조가 아니라 충돌을 줄이기 위한 예시다. 하나의 Spring 프로젝트 내 패키지 분리로 시작하며 멀티모듈/별도 서비스 전환을 요구하지 않는다.

```text
backend/
  auth/                 BE1: 이메일 자격증명·토큰·초대·실패 제한
  users/                BE1: 온보딩·취향 이력·시점 조회
  catalog/              BE1: 4축·8종·서버 config
  memories/model/       BE1: 공용 모델·저장/상태 primitive
  memories/creation/    BE1: 직접 작성·분석·안전 활성화
  memories/query/       BE2: 상세·보관함·내 기록·지도 읽기
  memories/lifecycle/   BE2: 삭제 use case(공용 저장 primitive 사용)
  images/               BE1: 임시 업로드·독립 복사·조회 Controller
  letters/              BE2: 일일 선정·수신·읽음·좋아요 transaction
  reports/              BE2: 접수·운영 사용사례
  contracts/            공동 계약, 파일별 주 담당 지정
  common/               C01~C09 담당표에 따른 구현
  db/migration/         각 담당 작성, BE1 번호/순서 관리
  tests/                각 담당 테스트, BE2 CI 통합
```

초기 계약 PR 이후 담당 기능별 작은 PR로 나눈다. BE1의 사용자·경험·파일 모델 변경, BE2의 일일 슬롯·권한·Idempotency 변경은 상대 담당자 리뷰를 필수로 한다. 실제 GitHub 이슈나 브랜치 생성·저장소 변경은 이번 문서 작업에서 수행하지 않았다.

### 13.3 자료와 산출물

`BE1_TASKS.md`와 `BE2_TASKS.md`는 이 문서의 동일 작업 ID를 추출한 개별 인계용 문서다. `SHARED_CONTRACTS.md`는 공통 모듈·포트·트랜잭션·합의 항목을 담는다. `TEST_OWNERSHIP.md`는 원본 테스트 담당표다. 원본 API·ERD·MVP와 GitHub는 수정하지 않았다.

**첫 실행:** 0~2시간에 현재 명세의 제안 항목을 합의 → 주 담당별 모델/포트와 Mock을 준비 → BE1의 계정/작성과 BE2의 선정/수신을 병렬 개발 → 연결 가능한 기능부터 실제 통합 → 좋아요·파일·날짜·권한의 공동 회귀 테스트 → 상태/미통과 항목을 기록하여 인계한다.
